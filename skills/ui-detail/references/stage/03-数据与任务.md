# 03 · 数据与任务

> **适用**：列表表格、上传、日期时间、拖拽排序、保存草稿要动手实现或验收时。
> **本轮不可交付时**：若这一轮没有任何集合或任务（没有列表、上传、日期区间、排序、草稿），停下并说明「没有集合与任务」，改读 [02-控件与交互](02-控件与交互.md)。
> **读完能判定**：列表能否扫读、排序筛选与返回是否保住位置；上传状态机是否分段、失败是否只重试失败项；日期语义与时区是否定死；拖拽是否既有替代路径也有取消路径；保存的三份版本是否分开。

列表、上传、日期、拖拽、保存的共同点：都有"集合与任务"的状态。变化之后，用户必须还能找到自己在哪、哪些成功、哪些要重试。

细则与理由：[11 表格与列表](../detail/11-表格与列表.md)、[14 上传与附件](../detail/14-上传与附件.md)、[15 保存与草稿](../detail/15-保存与草稿.md)、[16 日期与时间](../detail/16-日期与时间.md)、[17 拖拽与排序](../detail/17-拖拽与排序.md)。

## 列表与表格

- 先能扫读：文字列按阅读方向对齐，数值列向尾侧；金额统一精度与单位；未知 / 未填 / 数值零是三种状态，不都写成空白或 0。
- 日期列说明时区或使用场景；排序规则与展示格式不能互相矛盾，不要按本地化字符串字典序排序。
- 进详情用真链接（保留新标签打开、复制地址）；整行可点只能作辅助，行内复选框与菜单不得触发导航。
- 不要整行做成链接再嵌按钮；常规表格用原生 `<table>` + `<th scope>`，不因"可操作"就上 `role="grid"`（会承担完整键盘导航义务）。
- 行操作可在 hover 或行内 focus 时加强，但关键动作要能被发现并触屏可用；不可见按钮不许挡住文字。
- 排序/筛选要交代：当前列与升降序（`aria-sort`）、生效条件、排序变化后回到哪个页码。
- 搜索与筛选写入 URL 或历史状态，便于刷新与分享；先定义哪些状态必须可恢复。
- 从详情返回恢复查询、页码，尽量恢复滚动与焦点；后台插入新数据不能把阅读位置挤走，用"有新项目"提示让用户主动加载。
- "全选"必须说清范围：当前页 N 项，还是筛选后 M 项；跨页选择按稳定业务 ID 保存，不按数组下标。
- 部分选中用 `indeterminate`（通过 DOM 属性设置，不是 HTML 属性），并确保辅助技术能感知。
- 批量操作失败逐项记录：成功移出选择、可重试的保留并提供"仅重试失败项"、不可重试的说清原因、结果未知的先查询。
- 批量操作区出现时不要整体推下列表；预留工具栏或在原区域切换内容。
- 固定表头与固定列要有不透明背景与清楚层级；行内控件不能被吸顶表头或批量栏遮住（`scroll-padding` / `scroll-margin`）。
- 删除后焦点交给相邻对象的入口或稳定列表控件，不落回文档开头。
- 首次加载失败在表格区重试；加载更多失败保留已加载行、只在尾部重试；"筛选无结果"与"加载中"不能共用同一张空态。
- 更新单行不要整表卸载重建（会丢滚动、选区、焦点）；虚拟化用稳定键值，并接受浏览器查找与读屏的额外成本。

## 上传

- 选文件前说明：允许格式、单文件大小、数量、是否多选；`accept` 只影响选择器，不是校验也不是安全检查。
- 拖拽上传必须同时提供"选择文件"按钮；拖入无效类型说明原因，且不让浏览器直接导航打开文件。
- 状态机分段：待校验 → 排队 → 传输中 → 处理中 → 可用 / 传输失败 / 处理失败 / 已取消。传输 100% 不等于可用。
- 多文件各自保留状态与原因；总摘要可以是"2 个可用，1 个需要处理"，重试只针对失败项，不清空成功项。
- 给队列项稳定 ID，列表重排不得让进度串到别的文件。
- 已知字节才显示百分比；多文件总进度若按字节加权要说清它不是"文件数比例"；处理阶段用不确定进度 + 文字，不编造 99%。
- 取消传输、移除队列项、删除已保存附件是三个不同动作，文案与后果分开（后者通常是不可逆业务操作）。
- 同名文件先定规则（并存 / 覆盖 / 新版本 / 拒绝）；重复选择同一文件要区分"重试"与"新增"。
- 重试按任务或文件版本防重；超时先确认服务端是否已有对象，避免一次重试产生两份附件。
- 上传中关闭界面要明确：继续 / 暂停 / 取消；不承诺关页后普通脚本仍能完成上传。
- 失败原因具体（缺哪一列、什么限制），不只写"错误 500"；权限撤销或文件删除后旧预览要失效。
- 本地预览的对象 URL 用完 `revokeObjectURL`；不暴露服务端存储路径。

## 日期与时间

- 先定语义：纯日期（截止日、生日）/ 某时区的具体时刻（会议）/ 当地时间的重复规则（每天 09:00）。
- 纯日期不要交给 `Date` 构造器再格式化，避免跨时区差一天；按日期类型处理并约定序列化格式。
- "截止日当天是否还可提交"是业务规则，要写清；要求精确关闭时说明时区与时刻，不让前端猜午夜或 23:59:59。
- 手输与日历共用同一套限制；解析失败保留原文并说明原因，不"自动纠正"成另一天。
- 选中日期、当前日期、键盘活动日期是三个状态；翻月不等于选中。
- 禁用日期给原因（早于项目开始日期），手输也要拦住，服务端再校验一次。
- 区间定义统一：日历型行程常含结束日，查询区间常用左闭右开；显示天数与后端过滤、计价必须一致。
- 开始日期变化导致结束日期失效时，显式提示并要求修正，不静默改用户没注意的值。
- 夏令时会产生不存在或重复的当地时间：用地区时区规则，不用固定 UTC 偏移。
- 前端设备时间不可信；是否已过期由服务端规则判定，可显示"今天 18:00（北京时间）"并给完整日期。
- 列表显示、筛选、导出、详情用同一语义与时区，不要各处各猜。

## 拖拽与排序

- 先提供不用拖的替代路径："移动到"菜单、上移下移按钮、目标位置输入。键盘模式不能替代"无需拖动的单指针替代"要求。
- 状态链：静止 → 准备 → 拖动中 → 可放置 / 不可放置 → 放下保存 → 已确认 / 失败 → 取消回原位。
- 用明确手柄与移动阈值区分点击、文本选择、滚动与真正拖动；触屏长按不能破坏整页滚动。
- 拖动时保留原占位、预览跟手、插入位置清楚；无效目标明确拒绝，不靠颜色单独表达；松手位置必须与预览一致。
- 空列也要有可接收区域；跨列移动要说明是否改变状态、权限与字段。
- 边缘自动滚动只在合理区域启动、限制速度、离开即停；页面与内部列表都可滚时，明确哪一层接收。
- 提交按稳定对象 ID 与目标身份（邻居 ID / 排序键 / 版本校验），不提交"数组第 3 项移到第 5 项"。
- Esc、`pointercancel`、放到无效区域都要有明确结果；取消不发出隐藏的持久化请求；拖回原位通常不保存。
- 保存失败可回原位并说明，或保留待同步状态；不能静默回滚覆盖用户之后的另一次移动。
- 业务存在自动排序（按时间、名称）时不要假装支持自由排序；先说清拖动改变的是状态还是行序。
- 动画只服务位置理解：预览直接跟指针，其余卡片短过渡；减少动效时仍保留插入位置与结果。
- 结束后焦点留在移动后的对象，播报一次结果（"已移到已完成，第 2 项"），不是每像素一次。

## 保存与草稿

- 至少区分三份版本：当前编辑版、发送快照、已确认版。请求成功只确认那份快照。
- 当前内容与已确认版不同就继续显示未保存；不用全局 `saving = false` 抹平差异。
- 客户端自增版本只能组织本地状态；服务端乱序覆盖要靠串行保存 + 合并新修改，或条件更新/版本校验。
- 自动保存可防抖、失焦或显式提交，但输入值立即更新；IME 组合中不保存中间候选；校验未通过要说明"尚未保存：请修正日期"。
- "是否有改动"按版本与内容比较，不靠每次按键永久置 `dirty = true`（用户改回来后就干净了）。
- 重试说清是"保存当前内容"还是"重试刚才那次任务"；超时属结果未知，用幂等键、版本号或查询接口确认。
- 保存失败不清空表单；不用成功色显示"草稿已存本地"来伪装远端保存成功。
- 离线草稿写明"仅保存在此设备，尚未同步"，按用户与对象隔离，记录内容版本与时间；存储不可用要有降级。
- 恢复时比较服务端版本：没变可恢复草稿；变了提示冲突并允许查看或选择，不拿较新的本地草稿直接覆盖远端。
- 切对象或切路由时，在途回包不得给新对象标记已保存、不得把 A 的内容写进 B；请求与草稿绑定用户、对象与版本。
- 有未保存内容时提供保存 / 保留草稿 / 放弃三条路；`beforeunload` 只作补充，不承诺异步保存一定完成。
