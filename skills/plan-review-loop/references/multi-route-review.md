# 多路评审：分工、派发与汇总

## 职责分工

按主文件选定的路数安排不同的 Agent。分工规定各路优先检查的内容，不限制各路报告有依据的问题。

| 路 | 检查重点 | 应交付的依据 |
|---|---|---|
| 目标与实现 | 是否解决正确的问题且确实能实现：目标覆盖、事实与假设、实现入口、职责划分、现有机制复用、关键链路、验收有效性 | 目标与步骤的对应关系、源码或文档依据、遗漏的链路或约束、验收能否证明目标达成 |
| 运行与演进 | 投入使用、逐步切换及后续维护时是否仍成立：状态变化、依赖与消费者、兼容、部分失败与恢复、迁移与回退、维护成本 | 受影响消费者与生命周期场景、状态和版本过渡、失败恢复及回退依据、可重复验证方式 |
| 对抗 | 用反例检验当前方案的关键假设与失败路径 | 按[对抗路要求](adversarial-review.md)交付反例、依据及验证方法 |
| 替代 | 按改动尺度分三档：甲 换路线、乙 换组件、丙 不做／缩小 | 按[替代路要求](alternative-review.md)交付候选、比较及推荐；乙档须给「该决策点的成立条件」与「与其余条款的交叉清单」 |

“运行与演进”系统检查生命周期中的处理是否完整；对抗路主动构造具体反例，检验方案承诺能否被推翻。两路可接触相同主题，以检查重点和方法形成差异，不要求结论完全互斥。

按[主文件的核心任务与核心前提](../SKILL.md#核心任务与核心前提)组织核查：目标与实现路重点判断核心任务是否准确、必要条件有无依据、关键步骤能否产生目标结果；运行与演进路重点判断这些条件在切换、运行和维护中能否持续成立。对抗和替代路的具体方法见各自手册。

### 前两路的任务变体

主会话可按任务收紧前两路的重点，并在派发时说明各自要核查的问题。以下只是示例，不增加角色，也不要求每次套用：

| 任务 | 目标与实现侧重 | 运行与演进侧重 |
|---|---|---|
| 数据迁移 | 数据语义、转换正确性、目标数据是否满足业务约束 | 切换过程、兼容、增量同步、失败恢复与回退 |
| 接口改造 | 接口契约、调用链、目标行为与实现衔接 | 消费者兼容、版本共存、发布过渡与回退 |

### 聚焦核查与职责外发现

各路优先检查本路负责的内容，不必完整重复其他路的检查。如果发现本路职责外、有具体依据的高／中问题，也必须报告（复用路的完成标准见[主文件第 2 节](../SKILL.md)，不因此被要求全量扫描）。不要因分工而略过问题，也不要假定其他路会报告。

多路可以独立发现同一个问题，不要求各路结论互不相同。不要为了区别于其他路而编造问题。评价分工时，检查各路是否完成重点核查、提供独立依据，或补充了其他路未检查的内容。不要求独有问题数量或重合率达到某个指标。

## 派发与补路

按[评审协议](review-protocol.md)提供版本、材料和统一输入输出，追加该路职责。派发对抗路前，主会话及该路Agent读取[对抗路要求](adversarial-review.md)。升级时保留原路职责并补齐缺少的独立评审者。替代路开始前读取其专属手册。

### 复用还是换新

“复用”指同一路沿用前几轮的 Agent；“换新”指为该路起一个未见过历史版本的评审者。

| 职责 | 用谁 | 依据 |
|---|---|---|
| 首轮全部路 | 必须换新 | 换新只是提高盲度的手段；盲度由派发消息里有没有作者理由决定（见主文件第 2 节） |
| 复评“我提的问题是否真被改掉” | 复用 | 只有他自己持有证据链和旧版本；换新等于重查 |
| 复评“这一版有没有引入新问题” | **该轮至少一路换新** | 复用者对自己批准过的设计会形成盲区：它记得“这个设计我通过了”，于是不再问“这个设计还需要什么配套” |
| 跨版本一致性（谓词句是否逐字未变、真值表是否被翻） | 复用 | 没有旧版本的评审者做不了 |
| 某路连续两轮没有任何高／中问题 | 下轮换新 | 复用价值已耗尽；换人正好检验“是真没问题还是看惯了” |
| 版本跨度大（改换技术路线） | 全部换新 | 旧快照已无参考价值 |

每轮的最低配置以[主文件第 2 节](../SKILL.md)为准：一路换新做全量新问题扫描，其余路复用核对闭环表所引位置。换新者仍须拿到完整正文，但不必拿到历史意见。换人后记录里注明各路是复用还是换新，以及换新者看到的材料范围。

各路对共同正文形成独立结论后再汇总，不提前分享当轮意见。记录每路实际检查范围、版本及限制，区分新检查与旧证据复用。

## 汇总与复核

合并关于同一缺陷的重复意见。保留原问题 ID、提出问题的评审路，以及各路新增的证据、触发条件和影响。如果两个缺陷需要不同修复，不要仅因主题相同就合并。只有一路发现的问题或提出的异议，也必须保留，不按票数淘汰。事实争议用代码、约束或获准执行的验证解决，严重度争议请相关评审者复核。满足既定约束的方案偏好由主会话在授权范围内取舍。

**同一缺陷被不同路判到不同严重度时，采用较高者**，并把判得较低的那一路的理由记在旁边。若两路不是严重度不同，而是对同一结论的可行性判断相反（一路说“走不通”、另一路说“有可行路线”），不套本条，按[主文件](../SKILL.md)第 3 节争议表处理。降级只能由该路在复核后给出依据（“这段只是措辞，不改变任何拒绝条件”），不能由主会话按“多数路都判低”下调。反过来，判得较高的一路若给不出具体触发条件，由它自己撤回，主会话不代为降级。业务目标、扩权和已确认决策交用户决定。如果实质争议没有新证据，也没有可执行的解决动作，按主文件记录未决，不反复派发同一争议。

复评时，向本轮全部评审路提供完整新快照、合并后的问题和处理依据。扫描路检查全文与其改动影响，复用路检查闭环表所引位置及关联前提。对于未受影响部分，各路可沿用既有证据，但须确认仍适用，并注明原版本和覆盖范围。各路据此给出当前版本的结论。评审者必须核查实际处理结果，不能只接受主会话的“已处理”声明，也不能只转发旧的通过结论。

复评输出必须含**闭环表**（义务归复用路）：旧问题逐条给出 已关闭／部分关闭／未关闭，并附依据位置；扫描路未收到旧问题时写“本路无旧问题”。**没写依据位置的关闭不算关闭**——只写“已修复”而不指到具体条款的，按未关闭处理。
