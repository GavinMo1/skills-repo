# 设计理由与沿革（维护者文档）

**不是运行时指令。** 只有两种情况读它：要改某条规则，或想删某条规则。理由在这里，规则正文在 [主文件](../SKILL.md)；两处不一致以主文件为准，并回来更新这里。

## 每条硬规则防的失败

改规则前先确认它防的失败还存不存在。只是"看起来啰嗦"不是删除理由。

**有真实锚点的**——删之前先看锚点那一列：

| 规则 | 防的失败 | 锚点 |
|---|---|---|
| 判别表：新发现先分「能否实测 × 失败重数」 | 每个新发现都变成一节新正文，方案越修越不可实施 | 本 skill 自身改造：方案从 11784 字节涨到 29768 字节，17 版只增不减 |
| 作者不逐条枚举一致性结论 | 作者枚举的永远是他想到的那些，而新缺陷几乎总落在条款交界处 | 8 条实施期偏离里两条真缺陷（取舍点清单与登记表双写、逐轮存档自相矛盾）由复核方发现，作者自查未发现 |
| 改动面分报「新增位置」与「删除或合并」，不相抵 | 同一规则散在 N 处各自演化；只数条款数看不见，两数相抵更看不见 | `user-profile-repo` v1.0 的「容量触限三项」写在 3 处 |
| 预算写死 10 轮、三档相同 | "按轮次上限计"却从没给出数字，跑到那一步只好自己编，编出来没人复核 | 改造前主文件四处引用上限、全文无一个数字；用户当场定为十轮 |
| 两份产物按消费者分工：方案只放动作与判据，记录只放理由与历史 | 决策历史挤进执行 Agent 的上下文；反过来，记录长成没人读完的档案 | 用户 2026-11-24 指出原目标把消费者写成"用户" |

**只有推断的**——它们都是**删除候选，不是留存理由**：

| 规则 | 防的失败 |
|---|---|
| 核心前提给锚点 + 可证伪条件 | 用"看起来有依据"代替有依据；片段支持结论而全文推翻它 |
| 可执行行为类前提在隔离目录实跑 | 用读源码推断"脚本会这么跑"，运行时却走另一支 |
| 盲区表 + 移入盲区不算新增条款 | 作者不能承认"这里我不知道"，删减永远停不下来 |
| 闭环表 + 位置证据 | 只转发"已修复"，不指到条款 |
| 不按票数／平均分通过 | 用"多数路判低"掩盖真问题，最省事的收口变成默认 |
| 两路结论相反时要求最小验证 | 把可行性分歧当严重度分歧，用"取较高者"糊过去 |
| 盲度由派发消息内容定义 | 换了 Agent 就宣称盲评，独立评审退化成第二个复述者 |
| 每轮只一路全量扫描 | 全路重读，成本与收益脱钩；"是否真做了全量检查"不可观察 |
| 强度分三档、轻评四条逐条留痕 | 三行能说清的改动也要建表派两路，成本高到让人绕过评审 |
| 部分交付 | 80% 可开工的方案被整份退回，用户拿不到能用的部分 |
| 待核实事实默认代跑、不停在台账 | 一条命令能跑出的事实被当成偏好去问用户；用户答不出，同一个错结论反复出现 |
| 替代解法分甲乙丙三档 | 用"要不要加一路"一个开关处理三种尺度的改动 |

**样本一列怎么用**：有案例写锚点，没有的写"推断"，不得为填满而编案例。标"推断"的规则是删除候选——真挡下过一次就回来补锚点；一直补不上，下次动这份文件时优先删它，而不是替它设想还能防什么。**新规则例外**：刚加、还没经过一次真实使用的，标"推断（新，未到观察期）"，先给一次机会再判。

## 沿革：2026-11-24 改了两轮

同一个文件一天改两遍，第二遍纠的是第一遍没看清的消费者。下表只留会被误改回去的那几条。

| 改动 | 为什么原写法不划算 |
|---|---|
| 通过条件从"六条台账"收敛为两组：方案可开工（三问＋闸门）＋记录可审计 | 过程台账被当成通过判定，"建够表"冒充了"能开工" |
| 每轮六张表砍成闭环表＋修订表 | 真实风险只有"作者自说自话"，闭环表一张够用，其余是自证材料 |
| 低问题不逐条核证 | 对不参与任何判定的噪音付全额成本 |
| 评审者只报问题与两问句取值，不产出"能否收口" | 收口判据与通过判据不同源，同一状态两个答复 |
| **终局三问换成执行视角**（从哪开始／每步怎么判成功／哪里不能动缺什么必须停） | 原三问里的"当初为什么这么定"是审计者的问句，塞进执行侧后方案被迫自带历史，与"越来越短"直接互掐 |
| **决策登记表整张移入记录**，方案只留 `决策 N` | 依据锚点、性质判定、推翻条件挤占执行 Agent 的上下文 |
| 轻评不再"免决策登记表" | 表进记录后，豁免只为省方案篇幅；留着还漏掉"轻评答不出为什么这么定" |
| 新增「派发实施时的上下文隔离」「两份对得上」 | 对评审者写清了不给哪些材料，对实施者一条没有；决策一改，方案里引用它的句子没人管 |
| 记录按"主会话读哪几处、用户读哪几处"分工 | 十几项必备无消费者，会长成没人读完的档案 |
| 术语：放行项／触发项／死态／判死项 → 可披露项／必须改／不可清／一条判定 | 四个自造词互相解释，规则读不出动作 |

第二遍**没有加新机制**：真正新增只有三条（上下文隔离、同源校验、开工说明的完整格式），轮次、强度、闸门、替代三类都没动。

| 改动 | 为什么原写法不划算 |

## 已删除的规则：不得改回来

删掉时各自的保护意图都还在，只是换了机制实现。

- **固定三路**（"简单方案也用三路"）。意图成立，机制选错了：它取消判断，而不是让判断留下痕迹。现由三档承接——沉默跳过仍然违规，成本随风险变化。**轻评不是它的复活**：轻评要求四条同时成立并逐条留痕。
- **预算用尽后的 diff 复评（最多 2 轮）**。与"契约精度修订按普通复评""预算用尽交付未收敛"三处互相覆盖，同一状态出现三种答复，现场必按最省的解释。成本端已由"每轮只一路全量扫描"压下来，不需要第二个出口。
- **面积不增长（条款数＋参数数＋验收项数）**。计数诱使合并与改写来规避计数，"条款"也没有可数定义，最后变成一条被普遍忽略的规则。现由内容判据承接：删掉这条，会不会有执行 Agent 因此做错动作？
- **"第 3 轮两点满足即加第四路"**。只看方案是否通过，看不出问题性质，会把"方向正确、精度不足"的方案强制换路。现由"换不换路看改动尺度"承接。
- **通过闸写成"各路高0／中0"**。计数既是终点线，又被规定不得追求，最常见的结果是降严重度。现由闭环表承接：每条问题要有开／关判定，关闭项要指到正文位置，计数降为摘要。
- **两条停止判据的操作提示**（"连续两轮无高中问题关闭就冻结去实测"、"既无可删条款又只能靠新增"）。前者与"触发即继续"同状态相反，且它的收尾动作"写进已知盲区"被主文件第 1 节禁止；后者与"不靠新增条款回应新发现"同向，是重复条文。都现由"本轮没有任何可执行动作"承接。
- **路名写作 A／B／C**。甲乙丙上线后字母与档位对应关系已消失，留着只会让"路 C"和"丙档"被读成同一件事。
- **评分、加权、多数票**（未采纳，不是删过）。把"能不能直接开工"换成一个与它没有稳定关系的数，于是作者优化数、评审者优化数，而方案是否可实施无人负责；多数票则把"没人反对"当成"没有问题"，而单路发现的真问题恰恰是票数最少的那类。

**2026-11-22／23 的八次收尾**留下的教训，比那七次尝试本身有用：**判断一条判据能不能用，先看它的操作数是不是都在被评文本里**。闸门 ② 用了四版才发现它在问"用户说过什么"，那不在文本里；问句 ① 一直没出这类问题，正因为它的操作数（条文、对象、验收）全在文本里。2026-11-24 补的"旁注没有用户原话时怎么判"，是同一教训的第二次收尾。

**被否决的提议：免评审出口**（"单点修改、一条命令可验证、无选择点就直接做，不进评审"）。本 skill 由用户手动调用，不会被自动拉进任务，"小改也被拖进完整循环"这个失败不存在；加一条出口只会让"这次不想评审"变成默认。**不得加回来**——若将来它变成自动触发（例如写进 AGENTS.md 的常驻规则），这条要重新评估。

## 维护检查清单

1. **这条规则防的失败，现在还发生吗？** 发生过就保留并写清触发条件；只听起来稳妥的，删（新规则例外除外）。
2. **它会不会和已有规则给出不同答复？** 同一状态两种答复，现场一定选省事的那个。先消除冲突，再加内容。
3. **判断依据可观察吗？** "是否真正独立""是否理解了"不可观察；"派发消息里有没有作者的理由"可观察。不可观察的判据会被绕过。
4. **完成标准可检查吗？** "覆盖充分"不可检查，"每条问题有开／关判定且关闭项有位置"可检查。
5. **删掉的规则其保护意图由谁承接？** 没有承接就不得删；有承接必须在本文件记一笔，否则下一任维护者会把缺口当遗漏补回去。
6. **这次的改动能用一句话说清它改了什么判断吗？** 说不清就说明只是措辞变动，不得动结构。
7. **同一条规则只有一个维护点。** 详细分支放 references，主文件只留动作、条件、完成标准；主文件不写解释性段落——为什么，写在本文档。
8. **新增的判据，操作数都在被评文本里吗？** 需要外部信息才能判的问题会退化成反复重评。
9. **这条内容该归哪个消费者？** 方案侧只放"删掉它执行 Agent 会做错动作"的内容，其余进记录；判据句里不出现"人""读者""实施者"，写成执行 Agent／用户／主会话之一。

## 已知的残余风险

- **主文件 327 行／约 1.3 万字，已不是单页读完的体量**。2026-11-24 做过一次下沉（见上面第三遍沿革），剩下的多是每轮必判的规则；不得再拿字数当拆分理由，要拆先找"整节只服务一个判据"的段落，判断标准始终是每条规则的完成标准清不清楚。下沉带来的新风险是**指针化后没人读**。出现"照着主文件做完了，但没打开过 references"时，先补「什么时候读哪个文件」表的触发条件，不得把那节搬回主文件。
- **两份产物会漂移**。同源校验只在判交付时跑一次，实施期偏离可能让方案引用的编号在记录里过时。要盯的失败：方案里出现依据、理由、评审史（该在记录），或记录里出现只写给执行 Agent 的动作清单（该在方案）。把它搬回去，不得两边各留一份"以防万一"。
- **"评审者读方案＋决策部分、执行 Agent 只读方案"极易失守**：扫描路拿到评审史就不再是盲评，主会话图省事时会把整份记录塞给执行 Agent。两处都写了动作，但都是靠人执行的一次性检查，没有机制兜底；出现漏给或多给，先补派发模板，不得改成"干脆合并成一份"。
- **强度档位靠出错代价判断**，锚点已写成可列举条目（轻评四条、重评五类），组合判断仍会偏。要盯的失败是"轻评被当成少干活的理由"。出现"明明是共享接口却判了轻评"时，改那几条锚点，不得改成更抽象的原则，也不得退回"一律三路"。
- **部分交付与未收敛退出的边界**会把"处处都差一点"的方案拆成部分交付糊过去。出现时收紧到"已可开工部分的终局三问必须各有直接回答"，答不出就整份按未收敛退出。
- **替代路乙档"换组件"与对抗路"局部修复"在边界上重叠**；重叠不构成缺陷，两路结论一致时按合并处理。
- **统一 10 轮上限让轻评也能跑满 10 轮**。这不是许可：满足通过条件就该立刻停。要盯的失败是"反正还有轮次，再评一轮"——出现时不得动上限数字，先看该轮有没有可执行动作。
