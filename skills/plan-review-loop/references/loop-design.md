# 设计理由与沿革

**这是维护者文档，不是运行时指令。** 日常评审不读它；读它的时机只有两个：要改本 skill 的某条规则，或觉得某条规则多余、想删掉它。

理由在这里，规则的正文在 [主文件](../SKILL.md)。两处不一致时以主文件为准，并回来更新本文件。

## 每条硬规则在防什么

改规则前先确认它防的失败还存不存在。不存在才删；只是“看起来啰嗦”不是理由。

| 规则 | 防的失败 | 删掉会发生什么 | 样本 |
|---|---|---|---|
| 核心前提必须给锚点四件套 | 用“看起来有依据”代替有依据；片段支持结论而全文推翻它 | 评审变成措辞互评，谁也核实不了谁的断言 | 推断 |
| 可执行行为类前提须在隔离临时目录实跑 | 用读源码推断“脚本会这么跑”，运行时却走到另一支、exit code 非 0 或落盘字段缺失 | 前提的“已证实”退化成作者对代码的想象，方案按不成立的前提冻结，下游步骤全部带病 | 推断（新，未到观察期） |
| 判别表（能否实测 × 失败重数） | 方案每轮都在长条款 | 每个新发现都变成一节新正文，方案越修越不可实施 | 有：本 skill 自身改造中，方案从 v0.1 的 11784 字节涨到 v1.7 的 29768 字节，17 版只增不减 |
| 已知盲区表 + 移入盲区不算新增条款 | 作者不能承认“这里我不知道” | 承认无知的成本高于加机制，删减永远停不下来 | 推断 |
| 闭环表 + 位置证据 | 只转发“已修复”，不指到条款 | 复评退化成复述作者的说法 | 推断 |
| 不按票数／平均分通过 | 用“多数路判低”掩盖真问题 | 最省事的收口方式变成默认方式 | 推断 |
| 两路结论相反时要求最小验证 | 把可行性分歧当严重度分歧，用“取较高者”糊过去 | 分歧被数字消化，方向错误被计成“低问题” | 推断 |
| 盲度由派发消息内容定义 | 换了 Agent 就宣称盲评，作者的理由混进消息 | “独立评审”退化成第二个复述者 | 推断 |
| 每轮只一路全量扫描，扫描路读全文、复用路只读闭环表所引位置 | 每轮全路重读全文，成本与收益脱钩；“是否真做了全量检查”不可观察，会退化成口号 | 复用路被要求全量重读，成本回升，规则被绕过；或者复用路凭记忆判关闭，闭环表失去证据 | 推断 |
| 作者不逐条枚举一致性结论 | 作者枚举的永远是他想到的那些 | 修补引入的新缺陷几乎总落在条款交界处，而作者的系统性自查正是从这里漏过去；交界处的交叉改由复评方按闭环表和锚点核对 | 有：同一次改造的 8 条实施期偏离里，两条真缺陷（取舍点清单与决策登记表双写、逐轮存档一句自相矛盾）由复核方发现，作者自查未发现 |
| 替代解法分甲乙丙三档 | 用“要不要加一路”这一个开关处理三种不同尺度的改动 | 小事惊动整条路线重估，大事又被当成局部修补 | 推断（沿革：替换掉“固定三路”） |
| 评审强度分轻评／常评／重评三种，按出错代价选；轻评四条须逐条留痕 | 一个三行能说清的改动也要建表、派两路、过六条，成本高到让人绕过评审而不是减少评审 | 只剩两个极端：要么全流程，要么偷偷不做；「降路」重新变成作者的自由裁量 | 推断（新，未到观察期；观察点见「已知的残余风险」） |
| 部分交付（收口但通过条件不满） | 一份 80% 可开工的方案被整份退回，用户拿不到能用的部分，还误以为整份都不能用 | 状态机退化成二值，所有“差不多了”的情形被迫挤进通过或未收敛，两头失真 | 推断（新，未到观察期） |
| 待核实事实默认代跑核实，不停在台账 | 把一条命令就能跑出来的事实当成偏好去问用户；用户答不出，结论站不住，同一个错误结论反复出现 | 用户成了事实问题的兜底核实者；方案的可信度取决于作者猜得准不准 | 推断（新，未到观察期；来自用户 2026-11-22 的明确要求） |

| 改动面分报「新增写入处数」与「删掉条款数」，不相抵、各附清单、按本轮净新增计 | 同一规则被写到 N 处，任何一对失去同步就产生“同一状态两种答复”；只数条款数看不见，两数相抵更看不见 | 一条规则散在多处各自演化；净 0 时理由义务不被触发，而规则此刻已散在两处 | 有：`user-profile-repo` v1.0 的「容量触限三项」写在 3 处（决策 4 行／设计小节正文／验收落点旁注） |

本条与已删的「面积不增长」不同：那条要的是数字，于是诱发“合并以规避计数”；本条要的是**理由 + 清单**，且两数不相抵、口径是净新增。

**“样本”这一列怎么填。** 有具体案例的写锚点（哪次、哪个文件、什么数字）；没有的写“推断”，不要为了填满而编案例。这一列是为了让下面的维护清单第 1 条有东西可判：**标“推断”的规则是删除候选，不是留存的理由**——它听起来稳妥，但没人见过它挡下过什么。真发生了一次就回来补锚点；一直填不上，下次动这份文件时优先考虑删它，而不是考虑它还能防什么。**新规则例外**：本轮新增、还没经过一次真实使用的规则，样本写“推断（新，未到观察期）”，不计入删除候选——先给它一次真实使用的机会，再判它有没有用。

## 已删除的规则与删除理由

这些规则曾经存在，删掉时各自的保护意图都还在，但换成了别的机制来实现。不要在维护时把它们改回来。

**固定三路（“简单方案也用三路，不为简化任务减少路数”）。** 防的是作者用“这个很简单”逃掉评审。意图成立，机制选错了：它取消了判断，而不是让判断留下痕迹。现由“评审强度分轻评／常评／重评三种，按出错代价选，轻评四条依据逐条写明并写进记录”承接——沉默跳过仍然被禁止，成本随风险变化。**轻评不是这条规则的复活**：它要求四条条件同时成立并逐条留痕，删掉的这条则是把判断整个取消。

**预算用尽后的 diff 复评（最多 2 轮）。** 防的是在“为一行修订重开整轮”和“把未收敛写成通过”之间做不诚实的记账。但它与“契约精度修订按普通复评处理”以及“预算用尽交付未复评状态”两处互相覆盖，同一个状态下出现三种答复，现场必然按最省的一种解释。现在改的是成本端：每轮只有一路做全量扫描，一轮本来就很便宜，不需要第二个出口。

**面积不增长（条款数＋参数数＋验收项数）。** 防的是方案膨胀。但计数会诱发合并与改写以规避计数，“条款”本身也没有可数的定义，最后变成一条被普遍忽略的规则。现由内容判据承接：“删掉这条，会不会有人因此做错决定？”不会就不要加。

**“第 3 轮两点满足即加第四路”的机械规则。** 只看方案是否通过，看不出问题性质，会把“方向正确、精度不足”的方案强制换路。现由“换不换路看改动尺度”承接。

**通过闸写成“各路高0／中0”。** 计数同时是终点线，又被禁止追求（“不得为计数归零开轮”），作者被迫在“优化计数”和“别优化计数”之间做隐性选择，最常见的结果是降严重度。现由闭环表承接：每条问题都要有开／关判定，关闭项要指到正文位置；计数降为摘要。

**2026-11-22／23 八次收尾**：该行宣告“计数降为摘要”后，主文件第 4 节仍留着计数闸至少一轮。七个版本依次试过：计数闸换标签、另设判据甲乙（未落盘）、停止判据读闸门（缺判定主体）、补判定主体（同段两条相反）、`②` 三行折算表、`②` 加黑名单、`②` 加“无抄录即判不出”、放行项分甲乙两类。最终形态见主文件第 4 节第 2 条。**教训：判断一个判据能不能用，先看它的操作数是不是都在被评文本里**——`②` 用了四版才发现它在问“用户说过什么”，那不在文本里；问句 ① 之所以一直没出这类问题，正因为它的操作数（方案的条文、对象、验收）全在文本里。

**路名写作 A／B／C。** 三档替代改用甲乙丙之后，字母与档位的对应关系已经消失，留着只会让“路 C”和“丙档”被读成同一件事。现在三路一律用中文全名。

**停止判据的操作提示“连续两轮没有任何高／中问题被关闭，冻结去实测，剩余风险写进已知盲区”。** 与“触发即继续”在同状态相反；且它的收尾动作“写进已知盲区”被主文件第 1 节禁止——会让人做错决定的缺口不许以“已披露”名义移入盲区。现由“本轮没有任何可执行动作”承接：这类情形在效果判据下判不出动作，自然不再开轮。

**停止判据的操作提示“本轮既找不到可删或可合并的条款，又只能靠新增条款回应新发现，冻结去实测”。** 与第 3 节硬线“不靠新增条款回应新发现”同向，是重复条文；若一条发现确实只能靠新增条款且触发闸门，它现由“本轮没有任何可执行动作”承接——先答“为什么这里会缺 X”，删掉成因就属于有动作。

## 为什么不评分、不投票、不设加权

评分把“能不能直接开工”替换成一个与它没有稳定关系的数。一旦有数，作者优化数，评审者优化数，而方案是否可实施无人负责。同理，多数票把“没人反对”当成了“没有问题”，而单路发现的真问题恰恰是票数最少的那类。

## 维护检查清单

改这个 skill 时逐条过一遍：

1. **这条规则防的失败，现在还发生吗？** 发生过就保留并写清触发条件；从没发生过、只是听起来稳妥的，删（第 27 行的新规则例外除外：未到观察期的新规则先给一次真实使用的机会）。
2. **它会不会和已有规则给出不同答复？** 同一个状态下出现两种答复，现场一定选省事的那个。先消除冲突，再加内容。
3. **判断依据是可观察的吗？** “是否真正独立”“是否理解了”不可观察，作者既不能设定也不能证明；“派发消息里有没有作者的理由”可观察。不可观察的判据会被绕过。
4. **完成标准可检查吗？** “覆盖充分”不可检查，“每条问题有开／关判定且关闭项有位置”可检查。
5. **删掉的规则其保护意图由谁承接？** 没有承接就不要删；有承接就在本文件记一笔，否则下一任维护者会把缺口当遗漏补回去。
6. **这次的改动能用一句话说清它改了什么判断吗？** 说不清就说明它只是措辞变动，别动结构。
7. **同一条规则只有一个维护点。** 详细分支放 references，主文件只留动作、条件、完成标准。

## 已知的残余风险

- 主文件仍是单页读完的体量，长方案评审时会占用可观上下文；若将来出现“读了主文件就急着开工”的案例，先检查每节的完成标准是否清楚，再考虑拆分，不要为字数拆。
- 轻评／常评／重评的边界靠出错代价判断，作者仍有解释空间。锚点已写成可列举的条目（轻评四条、重评五类），但组合判断仍可能偏差。**要盯的具体失败是：轻评被当成“少干活的理由”**——出现“明明是共享接口却判了轻评”这类偏差时，改那几条锚点，不要改成更抽象的原则，也不要退回到“一律三路”的一刀切。
- 部分交付与未收敛退出的边界靠“有没有一块能独立开工”判断，同样会偏差，偏差方向是把一份处处都差一点的方案拆成部分交付糊过去。出现时收紧到“已可开工部分的终局三问必须各有直接回答”，答不出就整份按未收敛退出。
- 替代路乙档的“换组件”与对抗路的“局部修复”在边界上可能重叠；重叠不构成缺陷，两路结论一致时按合并处理即可。
