# 评审要点清单：守卫、清理表、可判断言与修订记录

读它的时机：派发评审、核对自己方案里的守卫写法与验收断言、编写每轮修订表。规则正文在[主文件](../SKILL.md)；这里是可逐条勾的检查单与判据示例。

写示例中的命令、错误文案、字段名都按被评对象替换；不要照抄成本项目的常量。

## A. 守卫与取值：会让方案静默放行或丢数据的写法

这一类的共同点：功能测试会通过，缺陷只在非法输入或边界输入上显形，因此必须由评审主动构造输入，不能等作者提出可疑点。

### A1 fail-open 守卫

```python
if isinstance(self.data, dict) and not v2_ok(self.data):
    raise SystemExit('需要版本2')
```

非 dict 账本让整个表达式为 `False`，版本门被跳过——恰好与“门覆盖全部写命令”相反。判据一句话：**把这个非法输入代进去，守卫是拒绝还是放行？放行即缺陷。**

要求作者改成显式的三段判断，并写明门落在哪个分支之后、哪些命令豁免（如 `init` 自己负责创建，不在门的范围内）。

### A2 存在性与 null 塌缩

```python
self.data = read_json(p) if p.exists() else None
if self.data is not None:   # 文件不存在 与 内容为 null 变成同一态
    ...
```

后果：方案里写的“拒绝 null 账本”按字面实现等于零改动，因为 null 和“不存在”走同一分支；内容为 null 的账本可能被初始化流程静默覆盖（旧内容只剩备份文件）。

改法：把“存在”与“内容”分成两个字段，三段守卫各自给中文错误：

```python
self.exists = self.path.exists()
self.data = read_json(self.path) if self.exists else None
# init:  if self.exists: raise '状态清单已存在'
# 其他:  if not self.exists: raise '先初始化状态清单'
#        if not isinstance(self.data, dict): raise '状态清单必须是JSON对象'
#        if not v2_ok(self.data): raise '需要版本2；旧版须依据历史迁移'
```

断言要分别覆盖四种输入：不存在／`null`／`[]`（顶层数组）／旧版本账本。每种都要求 rc≠0、中文错误、账本字节不变（对顶层数组还要求不出现 traceback）。

### A3 falsy 合并静默丢数据

```python
files = self.data.get('files') or {}      # 空 dict 也 falsy
```

写进取值器后，最普通的主路径（初始化 → 登记一条）会返回 `rc=0 saved:true`，而 `files` 仍是 `{}`——条目静默丢失，且只断言 `review`／`check` 的验收覆盖不到登记路径。

- 取值器缺键必须抛中文错误（`ValueError` 或等价），不返回空容器；
- `or {}` 只准出现在只读过滤处（遍历时不写回），并在正文指明是哪一处；
- 补两条断言：缺键时该命令 rc≠0 且账本字节不变；`init`→`register` 后条目数=1。

### A4 代码落点与豁免

插入一段守卫要说清落在哪里：**在“未初始化”守卫之后、命令分发之前；`init` 豁免**。放在最前的守卫会把“先初始化状态清单”这句明确错误换成 `AttributeError` traceback，用户看到的是栈而不是可执行的下一步。

### A5 顺序与回退的不对称

提交与回退常常不是同一顺序的逆操作：提交要借“新校验脚本 + 旧账本”这个仍可用的窗口（先换校验、后换状态），回退要借“旧校验 + 旧账本”（先回状态、后回校验）。反过来做会经过“旧校验 + 新状态”，所有命令一起报错，形成死态。

凡方案写了“先 A 后 B”，先在临时目录按两种顺序各跑一遍，记下每种顺序下每条命令的 exit code；写进正文时把顺序、窗口期禁止的动作、回退验收的夹具与期望码一起写死。

## B. 清理表与死态范围

“清理表”= 哪些状态／报错能用工具命令清掉、哪些只能手工改存储。它常被写成一张漂亮的表而实际不可执行。

### B1 按消息数核对，不按行数

- 表格条目数必须等于**代码实际产生的报错文案条数**：直接从产生消息的代码位置逐条抄，不凭印象列。表头写“N 条”时，表体合并行也会让核对者数错，机械核对一律按消息数。
- **重复文案按来源位置分行**。同一句文案可能落在多个字段（如 `files.X.owner`、`files.X.contributors[0]`、`reviews[0]`），可清性不同，必须分行并给判侧规则（例：`at` 以 `files.` 开头按作者侧、以 `reviews[` 开头按评审者侧；前缀按实际 schema 写）。
- **每条给可复制的清除命令**（含占位符），或明确写“无工具可清：只能手工编辑账本”。只写“重新登记即可”不算命令。

| 文案（原样） | 出现位置 | 可否工具清除 | 命令／处置 |
|---|---|---|---|
| 缺少当前内容通过记录 | `check --final` → `unchecked` | 是 | `state.py review --by <actor> --confirm-current` |
| 实体身份未知 | `reviews[0]` | 否 | 只能手工编辑账本 `actors`；占位值 `unknown-<来源>-<日期>` |

### B2 死态范围不得放大

- 能用命令清除的情形不得写成“死态／盲区”。典型错误：把作者侧与评审者侧的身份缺失并成一条，而作者侧其实可由 `register --actor` 改写、`unchecked` 归零。
- 真死态要写：为何无工具可清（哪个命令硬拒、拒在哪一行）、代价、什么条件下必须回来处理。
- 人工修复必须用**可追溯占位值**（`unknown-<来源>-<日期>` 一类），并在交付说明里写“未经核实”。禁止伪造一个看起来像真的身份或数值——后续任何检查都看不见它，问题会被永久掩盖。

### B3 机械动作先实测再写进正文

以下都属“文档里看着成立、跑起来不成立”的高发点，必须在临时副本上实跑：

- 已登记条目的类型／属性能否改（常见结论：不能，除手工改存储）；
- 已有 ID 能否被新记录复用（常见结论：不能，冲突报错）；
- 某项 exit code 的真实来源（是“清单已存在”，还是版本门？两者文案不同，断言写错会把两条路径混成一条）；
- 混批（新 old 代码与数据交错）下每条命令的实际行为：哪些 rc=1 不落盘、哪些 rc=0 并写盘。

实跑不成立就改写出口（换成真实可行的手工路径，或删掉这条出口），不把不存在的出路留在方案里。

## C. 验收断言可判性

### C1 三列，缺一不可

| 配方（具体操作序列） | 期望退出码 | 期望输出消息集 |
|---|---|---|
| ① `init` ② `register --kind shared` ③ `check --final` | 2 | `unchecked` 含“缺少当前内容通过记录”，且**不含**“没有登记文件” |

只给退出码的断言不合格：**两个不同原因常常同码**。典型例子是“漏搭一次评审”与“评审结论为需修订”都返回 rc=2——按码核对时，核对者会误判通过，而实际有一整条路径没被覆盖。同码必须靠消息集、落盘字段或条目数区分。

### C2 按消息数核对，不按行数

清单式核对（“清理表 9 条”“断言 5 项”）按消息数而不是表格行数：一行合并了两条文案、或两条文案恰好是同一句，都会让行数欺骗核对。能写成“由 X 全量统计得到，按类目拆解后各项之和等于总数”的，不要只给一个总数。

### C3 被引用的用例必须存在

写“由 T1／T3 覆盖”之前，先列完整用例表：编号、在哪个脚本、是否新增、覆盖哪条断言。以下都按未覆盖处理：

- 引用了不存在的编号；
- 用例存在但不检查这条断言；
- “由其他用例覆盖”而没有指明是哪一个。

新增用例数、独立脚本用例要单列，避免“新增 8 例”里混进本来就在的用例。

### C4 差异类断言用内容标记，不数条目

“改动差异逐行等于下列四项”这类断言会和真实 hunk 数**巧合吻合**：条目数对得上，内容却完全不同，核对者会误判通过。改成：

```
diff -U0 旧 新 | grep -c '^@@'   # 必须等于 4
每个 hunk 必须含指定标记行：
  hunk1 含 <旧实现的独特符号名>
  hunk2 含 <新调用点的独特片段>
  ...
某段声明为零差异（不计入 4）
```

零差异项要显式声明“零差异，不计入”，否则核对者会把“本来就一样”当成“改对了”。

### C5 覆盖面的自检

- 每条断言至少有一个用例能把它从“红”变“绿”：找不到能变红的输入，说明断言没测任何东西；
- 关键路径要有一条“成功但字段没变”的回归（例如注册后条目数=1），专门抓静默丢数据；
- 校验命令自身的退出码要有独立断言（空账本、缺键、非法 JSON 各一条），不靠“其他断言会覆盖到”。

## D. 「来源→修订」表

每轮评审后产出一张，**一行一条发现**：

| 来源 | 修订 | 是否改变实施动作 |
|---|---|---|
| R1F-02 | 状态入口守卫改成“存在／内容／版本”三段判断；§4 增 `__init__` 项；V11 增“`[]` 账本上 `next` 必须 rc=1 且中文错误” | 改（机制级） |
| R2F-01 | 回退验收补四个夹具与期望码（0／2／2／1），测试脚本纳入替换顺序 | 改（验收） |
| R2F-03 | 清理表补“当前内容尚无通过结论”，与相邻同义项合并为一行 | 不改（文档措辞） |
| R3G-09~12 | 记录区逐条补闭环行 | 不改（记录） |

写法要求：

- **来源**：评审路名＋稳定问题 ID；多路同指一条时并列（`R1F-02／R3G-04`），禁止写“各处”“相关意见”“按评审意见修改”。
- **修订**：落到哪一节哪一条、改成什么。写“已修复”“已处理”不算修订，也无法被复评核对。
- **是否改变实施动作**：只有 **改** / **不改** 两值。改 = 会改变实施时的命令、状态、顺序、验收判据或数据处置；不改 = 措辞、勘误、断言精度、记录补全、已进盲区、实施期可原位吸收。判不清时按“改”处理。
- 该列对应主文件第 4 节停止判据「本轮没有任何可执行动作」：整列都是“不改”，该轮即按无动作停；只要有一条“改”成立，就还有动作。
- 关闭状态不写进这张表，写进闭环表（逐条 已关闭／部分关闭／未关闭＋依据位置）。
