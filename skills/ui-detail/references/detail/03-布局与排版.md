# 03 · 布局与排版：让信息自然成组

> **适用**：页面「看着乱」但说不上哪错：间距没有尺度、同一区块对齐线太多、图标与文字总差一点、字号行高行宽不成套，或要定断点、紧凑模式与安全区。
> **不适用**：只是颜色不达标、要算对比度（04），或只是对齐之后焦点环与热区被裁（07）时。
> **读完能判定**：这处「乱」是间距问题还是对齐线太多，先减线还是先调值；这处该做几何对齐还是视觉补偿、补偿上限在哪；图标配多大字、viewBox 留白要不要计入；字号行高行宽是否成套、中文一行多少字；断点取在哪、容器查询还是媒体查询；紧凑行高会不会裁字。

[系列目录](../../README.md) · 上一篇：[导航与表单](02-导航与表单.md) · 下一篇：[颜色与对比度](04-颜色与对比度.md)

项目详情里，名称、负责人和截止日期的字号都一样，却依然可以有清晰层次。关键是先让用户看出哪些内容属于一组，再用字号和颜色表达组内关系。

## 间距先表达关系，再追求整齐

Label 到输入框 8px，字段之间 24px，区块之间 40px，是一组可尝试的起点。读者会把相近元素感知为一组，这叫亲密性（proximity）。若字段间距反而小于 Label 到输入框的距离，用户容易认错归属。

| Token | 起点 | 用途示例 |
|---|---|---|
| `space-1` | 4px | 紧凑的图标与文字 |
| `space-2` | 8px | 标签与控件 |
| `space-3` | 12px | 小容器内边距 |
| `space-4` | 16px | 列表项、紧凑卡片 |
| `space-6` | 24px | 字段组、标准卡片内边距 |
| `space-8` | 32px | 区块分隔 |
| `space-10` | 40px | 大区块分隔 |

4px 基准与 8px 节奏便于统一选择、降低随手取值的数量；它们不能保证任意缩放下都不出现半像素。奇数值也不天然错误，1px 边框、字号和视觉微调都有合理用途。

Gutter 是栅格栏间距，Margin 是元素外距，Padding 是内距。优先用父容器的 `gap` 组织同级元素，可以减少外边距抵消和首尾例外。

## 几何对齐：让边缘替你分组

间距决定谁被看成一伙，对齐决定这一伙看起来是否成立。反过来也常成立：**页面显得乱，往往不是间距不对，而是对齐线太多**——同一区块里有的元素贴 16px、有的贴 24px、有的自己居中，间距再标准也还是散。

人对齐很敏感。成排元素里 1–2px 的偏差会被看成“歪了”，所以先问“有没有一条共同的边”，再问数值。

可以这样判断：

- **减少对齐线，而不是给每个元素另找一个位置。** 一个区块通常一到两条纵向对齐线就够用。多一条线往往不是因为需要，而是因为没想清楚哪个是主角。
- **对齐要有参照物**：容器内边距、栅格、相邻元素。对齐到容器边缘比各自居中更稳。居中对齐适合短内容、成对元素、空状态和登录卡片这类居中式版面；长文本居中会让右缘参差、每行起点都不固定，读起来更累。
- **字身框不等于字面。** 中英文混排时，`text-align: left` 对齐的是文本框，字母 T、汉字左缘的侧边距会让“看起来的边”参差。这类差异靠容器内边距统一，不要逐字挪动。
- **对齐目标要选，不是统一规则**：Label 上置时对齐左缘，左栏式表单可右对齐 Label 去贴近输入框；表格文字列随阅读方向对齐，数值列向尾侧对齐。选哪种取决于参照系，不同参照系混用才会乱。
- **行首有额外元素时要换参照**：列表符号、序号、悬挂标点会改变行首的对齐对象，缩进应对齐到正文首字，而不是符号边缘。

这一节处理的是**坐标**：盒子边缘是否落在同一条线上。做完这一步，还会有最后一层偏差——线对上了，看起来仍然歪。这就是下一节要单独讲的问题。

## 视觉对齐：坐标对上了，眼睛还要认

先看项目详情里几个具体的位置。侧栏的星标图标与标题左缘同为 8px；播放按钮里的三角形图标和文字共用一套居中规则；主按钮上下 padding 相等；卡片的嵌套圆角按同心公式算过。截图放大到 200%，会看到星标像是往里缩了一点，三角形看着偏左，按钮文字略微偏上，卡片角上厚薄不均。数值都在，眼睛不认。

这类问题叫**视觉对齐**（optical alignment）：让眼睛感知到的边缘与重心对齐，而不是让元素的盒子坐标对齐。两者分叉的原因很具体——**盒子里装着看不见的空白**。文字的行盒在字面上方与下方各留了 ascent、descent 和行距的空间，字母左右还有侧边距（side bearing）；图标在自己的 viewBox 里常带一圈内边留白；三角形和圆形的墨迹本来就不铺满外接框。坐标对齐的是**包围盒**（bounding box），眼睛比较的却是**墨迹**（ink）和墨迹的质量分布，也就是视觉重心（optical center）。

判断顺序不能反：先问这条边该不该存在（上一节），再让数值收敛到少数几条对齐线（几何），最后才问墨迹是否也齐（视觉）。跳过前两步直接微调，得到的是好看的偏差，不是对齐。

常见的几种错位和可以先试的做法：

| 情况 | 只做几何对齐会怎样 | 可以先试的做法 |
|---|---|---|
| 圆弧字形 O、o、C、S 与直边字形 H、E 并排 | 圆弧的墨迹离边更远，看着内缩 | 字体本身已有 overshoot，通常不必额外补；要补的是自定义图形与图标 |
| 汉字与拉丁字母用同一字号 | 汉字字面率更满，看着更大更重 | 按字号角色统一，不逐字调；混排标题可微调字重或字距，看真实字形再定 |
| 圆形头像、圆形图标与方形元素同一左缘 | 圆心离边更远，看着缩进 | 对齐圆的最左墨迹点，或统一按圆形的视觉外框给容器定内边距 |
| 三角形播放图标、对勾、箭头、徽标 | 重心偏向底边或一角，看着偏 | 用 `translate` 做 0.5–1px 补偿，并在注释里写明原因 |
| 图标与文字水平并排 | 图标盒子留白不同，间距看着不等 | 按视觉尺寸选图标（如 20px 图标配 16px 文字），先用 `gap` 统一，再考虑单点微调 |
| 单行按钮、标签、输入框的文字垂直居中 | 行盒 ascent 与 descent 不对称，中文看着偏上 | 先做对称 padding 与稳定行高，再试 `text-box-trim`，最后才微调 1px |
| 卡片圆角内嵌子元素 | 内外圆心不重合，角上出现厚薄不均 | 用 `内圆角 = max(0, 外圆角 − 间距)`，并把边框宽度算进间距 |
| 2px 描边与 1px 描边并排 | 描边更重的那侧看着更大、更靠外 | 减 padding，或让描边向内（`inset` 阴影、负的 `outline-offset`） |
| 文字下方的下划线、分隔线 | 几何等距，视觉上要么贴住字脚要么离太远 | 用 `padding-bottom` 决定线的位置，而不是拿负 margin 硬拉 |
| 有阴影与无阴影的元素并排 | 阴影让元素看着更重、更大 | 统一阴影层级，或给无阴影一侧留出等量空间 |
| 0.5px 边框、奇数宽度、非整数缩放 | 1x 下糊成一片，2x 下才清楚 | 用整数档的 1px 或 2px；小数宽度只在确认过的 DPR 下使用 |

**图标与文字混排**看两件事：尺寸和位置。尺寸按视觉大小配，不看几何边长——常见起点是 20px 图标配 16px 界面文字、24px 图标配 20px 小标题；图标 viewBox 里若有 1–2px 内边留白，实际看起来会更小，要么放大，要么裁掉留白。位置看重心：星标、齿轮、铃铛、播放这一排图标的视觉中心各不相同，横向先用 `gap` 统一，纵向只有在某个图标确实看着偏上偏下时才做单点补偿。补偿只改绘制，不改命中区域与焦点环。

**按钮、标签与输入框里的文字**：上下 padding 相等不等于视觉居中，因为行盒里 ascent 与 descent 不对称，中文字形在行盒里通常略微偏上，带 descender 的字母和下缘不规则的符号又会往另一边拉。先做对称 padding 与稳定的 `line-height`；支持时可让 `text-box-trim` 直接裁掉行盒上下多余的空白，使盒高等于字面高，垂直居中对齐的就是墨迹。这个特性支持范围仍然有限，不存在时退回“对称 padding + 1px 微调”。

```css
.primary-button {
  display: inline-flex;
  align-items: center;
  gap: .5rem;
  padding-block: .5rem;
  line-height: 1.5;      /* 固定行高，避免字体回退时高度漂移 */
  min-block-size: 2.5rem; /* 保证热区，而不是靠 padding 撑出来 */
}

@supports (text-box-trim: trim-both) {
  .primary-button {
    text-box-trim: trim-both;
    text-box-edge: cap alphabetic; /* 按大写字母高与基线裁，中文需实机核对 */
  }
}
```

**形状的重心**：三角形播放图标的重心偏向底边，它的光学中心比包围盒中心略高，所以按盒子居中时看着偏下，需要在垂直方向补一点点；同尺寸的圆和方并排，圆看起来更小，圆形按钮里的图标可以比方形按钮里的略大一点，才显得一样大。对勾、箭头、加号、圆点各有各的重心，品牌图形和徽标同理。这类补偿按 0.5–1px（换算成 em 约 0.02–0.05em）小步调整，写成带注释的变量。

```css
:root {
  /* 视觉微调：数值是项目起点，需在真实字体与 1x/2x DPR 下核对 */
  --optical-icon-y: -.5px;    /* 星标重心偏上，向下半像素 */
  --optical-glyph-start: -.04em; /* 超大标题首字 O 的左侧留白 */
}
.icon-button > svg { translate: 0 var(--optical-icon-y); }
.display-title { margin-inline-start: var(--optical-glyph-start); }
```

**圆角嵌套与描边**：`内圆角 = max(0, 外圆角 − 两者间距)` 要把边框宽度也算进间距，否则角上会差一条边；它只是一层近似，圆角较大时内外弧的视觉厚度仍可能不均，可以用嵌套容器或调整 padding 再看。描边本身还影响视觉尺寸：1px 与 2px 描边并排、或相邻两块只有一侧带阴影时，重的那侧看起来更大、更靠外。`box-sizing` 管的是布局尺寸，视觉重量得单独平衡——常见做法是减 padding，或让描边向内（`inset` 阴影、负 `outline-offset`）。这条公式的近似性质，在“密度与几何细节”一节还会回到。

**下划线与分隔线**：文字下方那条 1px 线的位置，几何等距时看着可能贴住字脚，也可能离得太远，因为行盒底部还留着 descent 空间。用 `padding-bottom` 决定线落在哪里，不要用负 margin 把线硬拉上去。

**字面与字身框**：上一节说过 `text-align` 对齐的是文本框。这里补一条界限：这类差异应该靠容器内边距成批统一，而不是逐字挪；只有超大标题、品牌字这种“一字一议”的场合，才用 `-0.02em` 到 `-0.06em` 的负边距把首字拉到视觉边缘，并且只在字体确定之后做——换字体、换语言就失效。

## 怎么定这个偏移，才不是随手调

视觉对齐和“我觉得再挪一点更好看”之间需要一条界线。按三层处理：

1. **有规律可循的先按规律做，不靠眼睛。** 字体的 overshoot 已经内置，不要自己再加；图标的视觉尺寸、圆角内缩、描边补偿都是可复用规则，应该写进组件或 Token，让一批元素一起对上。
2. **能靠统一留白解决的，不要单点改。** 字面与字身框的差异、图标 viewBox 的内边留白，优先统一内边距和画布，改一处、对一片。
3. **只剩单点补偿的，才动 1px 级别，并写清理由。** 说不出理由的偏移是随手调，不是对齐。这也是它和“把数字调成整数”最重要的区别：前者有解释，后者只有结果。

具体做法与门槛：

- **幅度**：通常 0.5–1px，最多 2px，换算成相对单位约 0.02–0.05em。超过这个量级，多半是间距或参照系选错了，应该回去改布局，而不是继续挪元素。
- **一次只改一个自由度**：先横向后纵向，改完立刻和相邻元素一起看。单独盯一个元素，永远觉得“差不多了”。
- **在真实条件里看**：实际尺寸、1x 与 2x DPR、200% 缩放各看一遍。0.5px 在 1x 可能糊成一格，在 2x 才显形；非整数缩放会让同一个数值表现不同。
- **字体或字号一变就重看**：以 em 表达的补偿会跟着字号走，以 px 表达的不会；换字体后 side bearing 全部改变，旧的偏移直接作废。
- **写成可读的变量或注释**：`--optical-icon-y: -.5px; /* 星标重心偏上 */`。没有理由的魔法数，是下次重构时第一个被删掉的东西。
- **底线不能动**：热区、焦点可见性、文字对比和语义不因为视觉补偿而改变。为了“看着齐”把点击区域缩到 24×24 以下，或让焦点环被容器裁掉，是拿可用性换观感。

也有不该动的时候：

- **数据密集的表格**：逐列微调会让人以为数值不等，表格该靠对齐线和等宽数字。
- **多语言界面**：为中文调好的偏移换到英文、阿拉伯文会反向出错，用与方向相关的 padding 处理，别写死 px 偏移。
- **早期还不确定的界面**：字体、字号、真实文案都没定时，微调是在给还不存在的界面调参数。
- **语义与替代文本缺失时**：视觉再齐也不成立，那是[第 07 篇](07-无障碍.md)的事。

## 验收视觉对齐

不要只看“整体感觉”：把截图放大到 200%，沿元素墨迹的边缘拉一条参考线，看同一组元素是否共用一条线；在 1x 与 2x DPR 下各看一遍，半像素、缩放和小数宽度带来的细微偏差会在这里暴露，也顺便解释为什么有些数值“差一点”。

再补三种快检：

- **快速扫视或眯眼看**：细节糊掉之后仍然“跳出来”的那个元素，通常就是没对齐的那一个。
- **用真实内容代替占位文本**：`O`、`上海`、`100%`、`（3）` 这类边缘不规则的文字，比“项目名称”更容易暴露偏差。
- **临时显示墨迹边**：给元素加一条辅助 `outline` 或叠参考线，确认对齐的是墨迹而不是包围盒；检查完就删掉。

最后要反向检查一遍：这些补偿有没有把热区、焦点可见性和对比度弄坏。视觉对齐是最后一层修整，不是可用性的替代品；它也依赖人眼，不同人、不同屏幕的敏感度不一样，宁可少调、写明理由，不必追求把每个像素都调到理论最优。

## 布局工具各有职责

Grid 适合行列协同，Flex 适合沿主轴排布。两者可以嵌套，不必按“一个页面只能选一种”理解。

```css
.project-layout {
  display: grid;
  grid-template-columns: minmax(0, 1fr) 18rem;
  gap: 1.5rem;
}
.actions { display: flex; flex-wrap: wrap; gap: .5rem; }
@media (max-width: 52rem) {
  .project-layout { grid-template-columns: minmax(0, 1fr); }
}
```

这里的 52rem 是示例断点。把真实项目名、长按钮文案放进去，找到内容开始挤压的位置再决定断点。设计系统现成的断点有助于项目统一，但不是设备分类的自然定律。

组件在主区和侧栏之间复用时，可以用容器查询，根据实际容器宽度变化。媒体查询仍适合页面级导航和整体布局切换。

## 字号、行高与行宽要一起看

| 角色 | Web 起点 | 需要观察什么 |
|---|---|---|
| 辅助文字 | .875rem / 1.5 | 是否被低对比度进一步削弱 |
| 界面正文 | 1rem / 1.5–1.7 | 表单和短文本是否拥挤 |
| 中文长文 | 1rem / 1.7–1.9 | 换行是否容易追踪 |
| 小标题 | 1.25rem / 1.4 | 与正文能否区分 |
| 页面标题 | 1.75rem / 1.25 | 长标题换行是否重叠 |

表中斜线后是无单位行高。根字号若为默认 16px，1rem 对应 16px；不要为了换算方便把根字号固定成很小的值。

模数比例是建立字号阶梯的一种方法，也可以按语义角色直接定义。13、15、17px 并不违规。数字统一的目的，是让相同角色表现一致。

中文正文可以先试每行约 30–40 个汉字，再按字号、内容和屏幕调整；`ch` 基于数字“0”的字形宽度，不等于汉字数。支持时可用 `ic` 近似全角字宽，并配合最大宽度兜底。

```css
.reading {
  max-inline-size: 42rem;
  max-inline-size: 36ic;
  line-height: 1.8;
  overflow-wrap: anywhere;
}
.amount { font-variant-numeric: tabular-nums; }
```

等宽数字适合金额和计时器，但前提是字体支持；小数点对齐还要靠表格布局或拆分数值列。

## 字体不是一个 font-size

Font stack 是后备字体列表；x-height 影响拉丁小写字母的视觉大小，cap height 影响大写字母对齐。Tracking 对应整体字距，leading 对应行高，kerning 调整特定字形对。中文也有标点挤压等排版问题，不能简单归为“没有字偶距问题”。这些差异的一半原因是字形本身，另一半就是上面说的 side bearing 与光学重心，所以换字体常常要连带重看视觉对齐。

系统字体加载快，平台差异大；Web font 可控，但要衡量文件体积、子集和缓存。中文网络字体可以通过子集化使用，并非必然不可行。可变字体可提供字重和光学尺寸等轴，具体可调范围由字体决定。

正文可从 400 字重开始，标题试 600。细字重并非禁用项，但小字号中文在部分设备上确实更难读，需要实机比较。不要全局强加非标准字体平滑属性；macOS Mojave 移除次像素抗锯齿也不是仅发生在深色模式。

长文要留意孤行寡行。截断内容时提供查看完整内容的方法；关键金额、错误原因不能只剩省略号。

## 密度与几何细节

紧凑模式可以把表格行从 44px 改到 36px，同时保持字号。触屏模式仍需检查热区；多行内容也不能被固定行高裁掉。密度表中的“行高”应区分 CSS 文本行高与整行容器高度。

嵌套圆角可从 `内圆角 = max(0, 外圆角 − 两者间距)` 开始，这是同心几何的近似规则，不是所有视觉效果的定律；形状重心与包围盒不重合时的光学偏移，见上文“视觉对齐”一节。

移动端注意安全区与视口：`dvh` 跟随动态视口变化，适合需要铺满当前可见区域的容器；希望高度更稳定时可考虑 `svh`。Sticky 的问题常与祖先滚动容器、可滚动空间有关，不应一看到 `overflow` 就认定失效。

验收时使用长项目名、空字段、200% 缩放和窄屏。水平数据表可以单独滚动，页面其他内容应尽量正常重排。
