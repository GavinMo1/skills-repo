# 16 · 日期与时间：选得快，也不能差一天

> **适用**：实现或验收日期时间选择、日期区间、时区显示、重复提醒，尤其要定位「跨时区显示差一天」「区间算错天数」这类问题时。
> **本轮不可交付时**：若界面完全不出现日期、时间、时区或相对时间文案，停下并说明「无时间语义」，回 SKILL.md 按对象重挑一篇。
> **读完能判定**：这个字段是纯日期、某时区下的确定时刻，还是当地时间的重复规则，存储与序列化契约是什么；手输与日历是否共用同一套规则、解析失败是否保留原文；区间的闭合语义在显示、过滤、计价上是否统一、开始日期变化时是否静默改动；「今天」「刚刚」的基准与排序依据；截止时刻的关闭规则由谁定、禁用日期是否给原因。

## 一、先判

1. **按值的语义先分三类**（表见第四节）：出生日期、按天管理的截止日期 → 纯日期（如 `2026-10-23`），日历日期不暗中转换成另一时区的前一天；会议开始时间 → 某时区下的时间或确定的时刻，界面显示时区并说明远程参会者看到的当地时间；每天 09:00 提醒 → 当地时间的重复规则，说明用哪个时区、夏令时变化后是否仍为当地 09:00。
2. **截止时刻由业务规则定**：「截止日当天是否还可提交」不能靠前端推断；若要在某个瞬间关闭，写明时区与精确截止时间，不要让前端自行猜成午夜或 23:59:59。
3. **纯日期不许走「字符串 → 日期构造器 → 格式化」**：JavaScript 对标准纯日期字符串的解析有 UTC 规则，在部分当地时区显示可能变成前一天。按纯日期处理，或采用明确的日期类型与序列化契约。
4. **手输与日历共用同一套规则**：键入时给出明确格式；解析失败保留原文并说明原因，不要悄悄把无效日期「纠正」为另一天；显示格式可以本地化，接口格式应稳定，两者之间需要明确转换。
5. **选中日期、当前日期、键盘活动日期是三种状态**：翻到下个月不代表已经选择某一天；Esc 取消、Enter 确认、清空、恢复默认值要有一致约定；原生日期输入与自定义日历表现不同，按采用的控件模式验证。
6. **禁用日期要解释原因**：如「早于项目开始日期」，不要只用极淡灰色让用户猜；手输也必须执行同样限制，服务端再校验一次。
7. **区间先定闭合语义**：日历型行程常包含结束日期，查询区间和时间段又常使用左闭右开；显示的天数、后端过滤与价格计算三处必须统一。
8. **开始日期改动不许静默**：开始日期使结束日期失效时，清楚提示并要求修正，或按既定规则联动调整，不能静默改变用户没注意到的结束时间；空结束日期代表「未设置」还是「开放区间」也要明确。
9. **夏令时会产生不存在或重复的当地时间**：涉及这些地区的会议安排，由可靠的时区规则识别并提示，不要只保存一个固定 UTC 偏移——固定偏移无法代表完整的地区时区规则。
10. **相对时间也有基准**：跨午夜时「今天截止」可能需要更新；前端设备时间不一定可靠，最终是否过期由服务端规则决定；可显示「今天 18:00（北京时间）」并在需要时提供完整日期，避免「刚刚」「昨天」无法用于核对记录。
11. **列表显示与排序共用一个语义**：不要把本地化日期字符串按字典顺序排序；筛选日期、导出日期与详情页也不能各自使用不同的隐含时区。

## 二、做完的标准

- [ ] 三种语义各归其位：纯日期字段把设备时区换到另一个时区后仍显示同一天；会议时间在任何时区都显示为同一时刻并标注时区。
- [ ] 手输与日历产出同一条值：键入一个日期、在日历里点同一天，提交出的序列化结果逐字相同。
- [ ] 键入一个不存在的日期（如 `2026-02-30`）后，输入内容原样保留并给出原因，不会被改写成另一天。
- [ ] 翻月但不选择、Esc 取消、清空、恢复默认值各验证一次，键盘活动日期不会被当成已选值提交。
- [ ] 选 10 月 23–25 日后，显示的天数、后端过滤与价格计算三处对同一区间给出同一结果。
- [ ] 把开始日期改到结束日期之后：界面给出提示或按规则联动，结束日期不会在无提示下变化。
- [ ] 同一个纯日期在 UTC+8 与 UTC−5 下各看一遍，列表、详情与导出三处都是同一天。
- [ ] 夏令时切换日（不存在或重复的当地时间）验证一次会议时间提示。
- [ ] 跨年、闰日、跨午夜各走一遍，「今天」「刚刚」在跨午夜后按服务端规则更新。
- [ ] 只用键盘完成一次选择与一次取消；小屏下面板不遮住输入框，错误提示能被看到。

## 三、依据与数值

- 本篇不含门槛数值与 WCAG 条号；对比度、焦点与热区门槛在 04、05、07。
- 三类值的语义归属不是「标准要求」，由平台日期类型与项目契约共同决定；「截止日当天可提交」属项目起点，须写进业务说明而不是控件默认行为。

## 四、控件、表格与示例

| 需求 | 值的语义 | 界面需要说明 |
|---|---|---|
| 出生日期、按天管理的截止日期 | 纯日期，如 `2026-10-23` | 日历日期，不暗中转换成另一时区的前一天 |
| 会议开始时间 | 某个时区下的时间或确定的时刻 | 显示时区，说明远程参会者看到的当地时间 |
| 每天 09:00 提醒 | 当地时间的重复规则 | 使用哪个时区，夏令时变化后是否仍为当地 09:00 |

## 五、失败长相与边界

- **截止日和会议时间都存成一个时间戳，跨时区显示差一天** → 纯日期被当成确定时刻序列化。按第一节第 1、3 条分开处理。
- **区间算错天数（少一天或多一天）** → 闭合语义在显示、过滤、计价之间不统一。
- **改了开始日期，结束日期自己变了** → 没有提示的静默联动，用户没注意到。
- **夏令时那天的会议时间错一小时** → 只保存了固定 UTC 偏移，没有按地区时区规则换算。
- **无效日期被悄悄改成另一天** → 解析失败后「纠正」而不是保留原文。
- **禁用日期是灰的但不说为什么** → 只用极淡灰色表达禁用，也没在手输路径上执行同样限制。
- **「刚刚」「昨天」对不上记录** → 相对时间缺基准或没给完整日期。
- **边界**：原生日期输入的格式与面板由浏览器决定，键盘与格式行为要按实际控件模式验证；不能只测鼠标点某一天，键盘日历导航、小屏面板定位与错误提示都要走一遍。
