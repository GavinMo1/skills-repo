# 对抗路：用反例检验当前方案

## 定义与边界

对抗路检查当前方案。寻找会使关键假设、预期结果或失败处理失效的具体输入、状态和操作顺序。回答“这个方案在什么条件下会失败，依据是什么”。它挑战方案成立的条件，也可指出核心方向不可行；不预设方案必须有问题。

共同输入输出、严重度、授权、轮数与复评规则遵循[主文件](../SKILL.md)，角色协作见[多路评审](multi-route-review.md)。本文件只补充对抗审查方法。

对抗路交付可核查的反例及修复所需条件；[替代路](alternative-review.md)负责探索不同解法并比较取舍。对抗路可以提出局部修复，也可以指出局部修复不足；发现替代方向时另列线索，不把重新设计整套方案作为本路的必需产物。

## 如何构造有效反例

按[主文件的核心任务与核心前提](../SKILL.md#核心任务与核心前提)，优先尝试用具体场景推翻核心前提或关键因果关系：即使各步骤照做，核心结果是否仍可能不成立？再沿原始实现或资料构造失败路径，不只检查作者已经列出的假设。按任务选择相关切入点，不机械遍历全部清单：

| 切入点 | 要挑战的假设 | 可构造的场景 |
|---|---|---|
| 输入与状态 | 输入总是完整、合法，已有状态符合预期 | 空值、重复数据、历史残留、混合版本 |
| 顺序与并发 | 步骤按既定顺序发生且只执行一次 | 重试、重复触发、乱序、检查后状态变化 |
| 部分失败 | 中断后仍能恢复或保持一致 | 写入一半失败、超时但操作实际成功、回滚再次失败 |
| 边界与依赖 | 权限、外部契约或资源条件始终成立 | 权限变化、依赖不可用、容量或时限达到边界 |
| 验收与可观察性 | 验收通过足以证明目标达成 | 测试通过但遗漏消费者、只核对声明或表面状态 |
| **条目内部自洽** | 规则、性质、断言三者一致 | 把同一节的“规则”与其下“性质/断言”逐条代入同一输入：例如规则写 `has(x) 即拒绝`，性质却要求 `has(x) 时放行且不计费`；或规则要求“失败不扣额”，而某维度按状态转移扣费 |

**“条目内部自洽”要单独查，不要指望它被其他切入点覆盖。** 这类缺陷不需要外部输入，只需要两句话相互代入；而其他切入点都从“外部世界怎么打破它”出发，会从旁边绕过去。同一份文档被反复修补时，新缺陷最常落在这里：修补者只读了自己改的那一段。

对每个候选反例，检查以下三点：

1. 该场景是否可能在当前范围内发生。
2. 实际执行路径是否存在，或方案是否遗漏了必需处理。
3. 后果是否违反用户目标、约束或方案承诺。

不要仅凭“理论上可能”就宣布存在缺陷，也不要以发生概率低为由忽略有证据的严重后果。

如果方案尚未实施，可以根据已有实现、依赖方约定和计划步骤推导后果。将结论标为“方案推演”，不要写成已复现的运行结果。证据不足时列待核实假设及最小验证，不编造调用路径或实测。

## 反例输出

沿用主文件的缺陷条目，补足以下证据链，无须另造一套计数：

> 被挑战的承诺或假设 → 具体触发输入／初始状态 → 操作或调用顺序 → 失效点及可观察后果 → 原始依据 → 最小验证 → 修复所需条件。

例如，方案声称“失败后重试不会重复扣款”，但只规定“调用扣款，成功后写完成标记”。评审者构造以下顺序：扣款成功，写标记前进程中断，恢复后重试。检查系统是否已有幂等键或去重记录，再判断是否会重复扣款。如果已有机制排除了重复扣款，说明排除依据，不把该场景列为缺陷。

## 核查纪律与复评

- 用具体证据挑战假设，不以强硬语气、泛泛风险清单或换个措辞重复其他路结论充当对抗。与其他路发现相同缺陷时，提供独立核查依据即可，不为独特性编新问题。
- “存在另一种写法”本身不是缺陷；审查强度不等于缺陷数量。没有成立的反例时，说明实际检查过的关键假设、被排除的场景及核查限制。
- 验证时，优先使用能回答当前问题的只读检查、推演或隔离样例。如果需要执行操作，遵守主文件的授权与代跑规则。不要通过破坏真实数据或执行计划中的实现来证明观点。
- 复评重新检查原触发条件是否仍能造成后果，以及修复是否引出新的失败路径；不能仅凭新增了一句“处理异常”就关闭反例。
