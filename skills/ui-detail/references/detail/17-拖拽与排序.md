# 17 · 拖拽与排序：拿得起、放得准、退得回

> **适用**：实现或验收可拖拽列表、看板跨列移动或手动排序，要判定拖到哪、能不能放、取消与保存失败分别怎么收尾时。
> **不适用**：界面只是固定顺序展示、没有拖动或跨列移动时。
> **读完能判定**：是否提供不用拖也能完成的替代路径、键盘模式是否写清；拖动各阶段是否保留占位与跟手预览、插入位置是否可辨、无效目标是否不只靠颜色表达；目标位置语义、跨列是否连带改状态与权限、空列能否接收；取消路径是否都回原位且不发隐藏请求；提交按什么身份、保存失败是回原位还是待同步。

把项目卡片从“进行中”拖到“已完成”，并不是让卡片跟着指针移动就结束了。用户需要知道哪里能放、放下会发生什么、不想移动时如何退出，保存失败后又会怎样。

## 先提供不用拖也能完成的路径

给卡片提供“移动到”菜单、上移下移按钮或目标位置输入。键盘与触屏用户都能完成同一任务，精细排序也更容易。WCAG 2.2 的拖动动作要求在适用条件下提供无需拖动的单指针替代，不能只加键盘操作就认为全部满足。

若同时提供键盘拖拽模式，要清楚说明拿起、移动、放下与取消的按键，并反馈当前位置。不要随意复用已废弃的 ARIA 拖拽属性；优先选成熟实现并实际使用读屏器验证。

## 一次拖拽的状态

```text
静止 → 准备拖动 → 拖动中 → 可放置 / 不可放置
                         → 放下后保存 → 已确认 / 保存失败
                         → 取消 → 回到原位
```

准备阶段区分点击、文本选择、滚动和真正拖动。可以使用明确手柄与合理移动阈值；触屏长按需要与系统菜单、页面滚动协调，不能一碰卡片就禁止整页滚动。

拖动时保留原占位，避免列表不断塌陷。预览跟手，目标插入线或容器高亮清楚可辨；无效目标明确拒绝，不靠颜色单独表达。放下后位置应与预览一致，不能松手才跳到另一处。

## 目标位置应可预期

排序列表要说明插在目标上方还是下方；跨列移动要说明是否改变状态、权限和字段。空列也要有可接收区域，否则没有卡片就无法拖进去。

边缘自动滚动应只在合理区域启动，限制速度，离开边缘即停止。页面和内部列表都是滚动容器时，要明确哪一层接收滚动，防止预览与真实位置分离。

如果业务会自动按时间或名称排序，不能假装允许手动自由排序。先改变排序模式，或清楚说明拖动改变的是状态而非永久行序。

## 能取消，也能恢复

Esc、失去有效指针序列、`pointercancel`、放到无效区域，都应有明确结果。取消回到开始前的位置，不应发出一次隐藏的持久化请求。拖回原位通常无需保存。

提交时按稳定对象 ID 与目标身份记录，不能只提交“数组第 3 项移到第 5 项”。并发更新后下标可能已经改变；持久排序协议可采用邻居 ID、排序键或服务端版本校验，取决于后端契约。

保存失败时，可以回到旧位置并说明，也可以保留待同步状态并提供重试；不要静默回滚覆盖用户之后的另一次移动。新旧操作要有关联和版本管理。对象在拖动期间被别人删除或失去权限，也需要清楚解释。

## 动画服务于位置理解

预览追踪指针应尽量直接，不把每个位置样本排成弹簧动画。其他卡片让位可用短过渡；放置与取消可以适度回到目标，但逻辑结果不能依赖动画结束。

减少动效时仍保留插入位置、目标状态与最终结果。拖动结束后，把焦点留在移动后的对象或合适入口；播报“已移到已完成，第 2 项”等简短结果，避免每一像素移动都播报。

## 验收路径

分别用拖拽和“移动到”完成跨列移动；拖到空列、无权限列、视口边缘；在过程中按 Esc、滚动、切出窗口；放回原位；让保存失败；快速连续移动同一对象。确认位置可预期、取消不提交、失败可恢复，触屏滚动也没有被全局破坏。
