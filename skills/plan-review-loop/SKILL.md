# 方案写评闭环

主会话编写方案，核实评审意见，并在授权范围内选择解法。独立评审 Agent 检查方案依据，提出问题，并复核修改。评审不代替用户授权。

**用词**：**一路**是一个独立评审分工，由一名 Agent 承担；**一轮**是全部评审路对同一冻结版本完成的一组评审；**一档**是替代解法的甲／乙／丙三种改动尺度，与轮次无关；**收口**指本轮不再修订、转入交付或实测，不等于“通过”（见第 4 节）。

## 启动与范围

- 如果已有方案，先读取原稿和评审记录，再继续工作。核对用户目标、范围、约束和已确认决策。信息足够时直接开始；缺失信息会影响方案选择时，才向用户提问。
- 用户指定的评审人数、严重度、轮次和结束条件优先。如果用户指定正式领域流程，按该流程分工和检查，不另加一套审批。普通微调或直接实现请求不自动增加方案审批。
- **路数由方案失败的代价决定，选择依据写进记录。**
  - **两路**：改动可逆、限于单文件或单模块、不改变用户可见行为、无迁移与切换。用「目标与实现」＋「对抗」。
  - **三路**：涉及共享接口、数据迁移、切换与回退、不可逆操作或多人协作。用「目标与实现」「运行与演进」「对抗」。
- 无论几路，降路必须写明上面哪几条成立；不得降到一路（用户明确指定单路评审时除外，须在记录里写明）。
- 各路一律用上述中文名指代，**不要写成 A／B／C**——三档替代用甲乙丙，混读会让“路 C（对抗）”与“丙档（不做／缩小）”被当成同一件事。
- 启动时读取[分工与汇总](references/multi-route-review.md)；冻结、派发或恢复时按需读取[评审协议](references/review-protocol.md)的对应章节。派发对抗路前，主会话与该路 Agent 读取[对抗路要求](references/adversarial-review.md)。启用替代路任档时另读[替代路要求](references/alternative-review.md)。修改本 skill 的规则、或想删掉某条规则时，读[设计理由](references/loop-design.md)；日常评审不读。
- 写方案正文前先建**决策登记表**：列出 3–5 个关键选择点（那些一旦选错、后续步骤全要改的地方），每点编一个稳定编号（决策 1、决策 2…），写“选定实现／依据／什么证据会推翻／备选”。它是替代路 乙档与对抗路的共同靶子，也是改动的边界：实质修改应能落到某个决策点上，落不到就要说明为何是兜底修正。
- 首次派发时，向至少一路明确问一次“不做这个方案、改用现有能力或缩小目标，能覆盖多少需求”（替代路 丙档）。同一个目标往往已有现成机制覆盖大半，这类候选比其他候选更便宜。

## 核心任务与核心前提

**核心任务**是用户最终必须实现的结果。**核心前提**是结果能够成立的必要条件；缺少它时，依赖它的后续步骤即使正确，也不能实现结果。

写方案时，说明核心任务、核心前提和每个前提的依据。用“已证实／待核实／明确不满足”标记前提状态。标“已证实”的核心前提必须给锚点：`文件 :: 符号名`，加一句可证伪条件（“若在该符号内找不到 X，则本条不成立”）。其余断言只需注明依据类别，不必逐条给锚点——证据要求针对核心前提，不平摊给全文。核心前提被证伪会改变某个决策时，正文只引用决策登记表的对应编号，不另写一份推翻条件。

区分目标本身的必要条件与当前解法依赖的条件。替代解法可以消除当前解法的依赖，但不能降低用户目标。不要把全部步骤和一般质量偏好都列为核心前提。

各路独立检查必要条件是否遗漏、误认或缺少依据。如果某个必要条件不成立，指出该条件为何必要、有什么证据，以及哪些步骤依赖它。优先处理这个阻塞，继续不受影响的检查。待核实不等于失败；尚未执行的检查仍记为未完成。

核心前提被证伪时只有两条合法出路，不得含糊放行：

- **消除依赖**：改用不依赖该前提的解法（见替代路 甲／乙档）；
- **降级为已披露的残余风险**：仅在前提对本目标不可满足时成立——例如它由上游语义决定（“这类消息在结构上就是用户消息”）、或由用户已确认的范围决定。降级须同时给出：不可解的理由、缓解措施、以及能核查缓解是否生效的验收项，写进风险清单，不得据此声称前提成立或把它改成“部分满足”蒙混过去。

评审者不得反复要求解决一个已被合规降级的前提；主会话也不得用降级绕过本可消除的依赖。

## 轮次与替代路

每路由一名 Agent 承担，不同评审路使用不同 Agent。主会话自评不能充作独立一路。满足通过条件后立即结束，不要求用完预算；轮次上限的用法见第 4 节。

预算用尽后不再开轮：按第 4 节交付未复评状态，不宣布通过。只改一行的修订也按普通复评处理，不另找快速通道。

替代解法按**改动尺度**分三档，触发条件不同，不要用一个笼统的“要不要加一路”来判断：

| 档 | 何时启用 | 成本 |
|---|---|---|
| **甲 换路线** | 有依据表明当前解法依赖的核心前提不成立；或当前解法没有可执行的修复动作，但目标可能通过其他机制实现 | 高：需首次盲评 |
| **乙 换组件** | 每轮都可启用；尤其当同一决策点已被修补两次以上仍未稳定 | 低：直接给候选与推翻条件 |
| **丙 不做／缩小** | 首次派发时强制问一次；之后按需 | 极低 |

各档替换什么、判据与例子见[替代路要求](references/alternative-review.md)。

换不换路看改动尺度，不看方案是否通过：**出现甲档触发条件时立即启用甲档；否则作者每轮自问“本轮的争议是否集中在一个决策点上”，是则启用乙档**。

未启用 甲档时，作者须在记录里写明判断依据（哪个决策点还没被质疑、哪些证据支持方向成立），不得沉默跳过。乙档与丙档**不新增评审路、不占额外轮次预算**：由现有某一路兼任，探索与对照合起来仍是该路的一项产出。甲档的盲评阶段与对照阶段合起来算该轮的一路，不另计一轮；在轮次结束后才启用甲档时，计入下一轮，不回填旧轮次。

启用后，在本循环中保留替代路；每次收到新快照时更新比较，不要求每轮提出新候选。用户固定了路数或设置了更早上限时，遵守该约束，并说明因此没有增加替代路。

若目标本身的必要条件只能由用户决策或外部证据解决，不强迫替代路绕开该条件。按退出条件交付阻塞状态。

换人、恢复执行、增加评审路或切换解法，都不重新计算已用轮数。在一轮结束前可以针对同一版本增加评审路；一轮结束后再增加，计入下一轮，不回填旧轮次。某一路失败时，其职责由下一轮的换新路补上；该轮记为未完成，仍计入已用轮数，但失败路不记成“无问题”。

## 1. 编写并冻结方案

核对原始需求、当前实现和现有机制。区分已核实事实、待核实假设和拟议行为。方案需说明目标、前提、范围、需要修改或复用的位置、关键步骤、兼容及失败处理、验证和验收标准。简单方案可用几段写清。

复用已有方案及项目文档约定。无约定时使用清晰命名的 Markdown 文件；用户只要对话稿或禁止落盘时保留完整对话稿。方案状态与实现状态分开记录。

默认使用**固定版本号和可复现的完整快照**：快照即本轮评审的完整正文，在收到全部评审结果前不修改。

影响行为、约束、前提、步骤或验收的修改称为**实质修改**。每次实质修改后，保存新版本并复评；交付前核对正文与最后被评版本是否一致。不改技术含义的「契约精度修订」（消除二义、修引用与常量自洽、收紧断言）仍升版本，但按普通复评处理，不另设快速通道。

版本号、正文标记、哈希口径与审计快照见[评审协议](references/review-protocol.md)「版本与快照」与「审计快照与哈希」。

方案正文必备一节**已知盲区**，逐条写「盲区名／为何暂不处理／代价／什么条件下必须回来」。移入盲区表不算新增条款，因此“承认这里不知道”永远比“再加一条机制”便宜，删减才停得下来。前提是**该缺口不会让人做错决定**：会让人做错决定的按中问题处理，不许以“已披露”名义移入盲区。

## 2. 派发独立评审

**每轮的最低配置**：一路未见历史版本的评审者做全量新问题扫描——重读全文，报告新问题；其余复用路只核对闭环表——读正文以核对所引位置，但不做全量扫描，也不承担提出新问题的责任（看到职责外的高／中问题仍要报告）。扫描路的完成标准是全文，复用路的完成标准是闭环表覆盖的位置。复用还是换新的依据见[多路评审](references/multi-route-review.md)。

首次派发时优先使用未包含此前方案讨论的新上下文。**盲度由派发消息的内容决定，不由换了哪个 Agent 决定**：消息里只含目标与约束、材料入口、本路职责、冻结正文（含其中已写明的依据锚点与决策登记表）、核心前提及依据；不含评审历史、作者对评审意见的取舍叙述，以及“我们讨论后决定”这类话。派发前把消息读一遍，删掉属于后者的句子。不传其他路当轮结论。不得仅凭“换了个 Agent”宣称盲评成立；工具确实无法隔离上下文时，说明已暴露的材料。**这条只约束首次派发与每轮的扫描路**；复用路必然持有旧意见，其材料见下条。替代路中只有甲档在首次启用时做一次盲评，之后复用同一评审者；乙／丙档直接给候选与对照，不隐藏当前方案。

每路获得的材料模板见[评审协议](references/review-protocol.md)「派发材料」。复评时，复用路另附旧意见处理记录；扫描路只附改动清单与改动面，不给旧意见——若确实需要它读闭环表，即为放弃该路本轮的盲度，在记录里写明。

输出需包括结论、高／中／低问题计数、有稳定 ID 的问题及依据、检查范围和限制。评审者只读评方案，不修改原文件、不执行拟议实现、不继续派 Agent，也不替用户批准上线。

严重度统一为：

- **高**：核心方向不可行、明显违反目标或授权，或可能造成严重破坏。
- **中**：会导致实施错误、关键兼容断裂或无法验收的具体缺口。
- **低**：不阻碍正确实施的清晰度或维护性建议。

只报告有依据的问题，不要求达到某个问题数量。如果评审者需要运行命令才能核实问题，但没有相应工具，应列出所需命令及其目的。主会话只在已有授权内代为执行，再将原始结果交给评审者核实。

## 3. 核实意见、修订并复评

逐条核对问题证据。高／中问题成立时，修改完整方案，并更新相关步骤和验收标准。根据改进收益决定是否修改低问题。合并重复问题时，保留问题来源和各路新增证据。不因只有一路提出问题就忽略它。

按以下方式处理争议：

| 类型 | 处理 |
|---|---|
| 事实或严重度争议 | 主会话提供原始依据，请提出问题的评审者复核。如果证据不足或实质争议尚未解决，保留未决状态，不自行降低严重度或删除问题 |
| 满足既定约束的方案偏好 | 主会话可在授权范围内选择解法，并说明理由。存在更优替代解法，不代表当前方案有缺陷 |
| 两路对同一结论判断相反 | 不取多数、不取较高严重度。要求双方各给一个可判定的最小验证（一条命令、一个输入、要读哪个符号）；主会话在授权内执行一次，把原始结果交双方复核。构造不出验证的，记为未决并列入交付——属于第 4 节退出清单里的“争议无法解决”，按未收敛交付，不标通过 |
| 业务目标、扩权或推翻用户决策 | 列出选项和影响，交用户决定。继续不依赖该决定的工作 |

每次实质修改后，主会话向本轮全部评审路提供新全文和修改说明。扫描路重读全文，自行判断改动影响；复用路核对闭环表所引位置及其关联前提与关键步骤。

**每项实质修改都要声明本轮改动面**：触及哪几个决策点、是否新增机制（几个；新参数／新状态／新依赖／新时序各计一个）。作者不逐条枚举一致性结论；交界处的交叉由复评方的闭环表与证据锚点核对（见评审协议）。

改动面受两条硬线约束：

- **不靠新增条款回应新发现**。判据是内容不是计数：删掉这条，会不会有人因此做错决定？不会就不要加；两条规则在说同一件事，先合并再改。不统计条款数。
- **单轮最多新增一个机制**。“机制”指需要新状态、新参数、新依赖或新时序的改动；单纯增加一个动作步骤不算，但同一轮新增动作超过两处，先合并再改。

超线时先删或合并再改，不写成“下轮注意”。

新发现必须先过一道判别，再决定它进正文还是别处——**能否被廉价实测发现？失败是单点还是灾难性的？**

| 能否实测 | 失败重数／严重度 | 去向 |
|---|---|---|
| 不能（授权、语义、数据模型） | 多，或有一个灾难性 | 写进正文 |
| 不能 | 单点、不灾难 | 写入已知盲区，一句话 |
| 能 | 任意 | 写成**判死项**：一句可执行的判定（什么输入／状态下直接判失败）＋一句兜底动作，不写机制 |
| 能且已知答案 | — | 写成常量或默认值，不讨论 |

这一栏是止膨胀的主要手段：绝大多数“看起来该写进方案”的发现，正确答案是判死项、常量或盲区，不是新条款。

未受影响的部分可沿用既有证据，但须确认仍适用并注明原版本与覆盖范围；只转发旧的“通过”不算当前版本复评。修改跨越多个模块、或改变核心前提与技术路线时，相关路扩大检查范围并处理新出现的高／中问题。评审者必须核查实际修改，不能只接受“已修复”声明。沿用与扩范围的细则见[评审协议](references/review-protocol.md)「复评与证据沿用」。

每轮记录按评审协议的「最小记录」执行。用户打断或上下文恢复后，从记录与实际 Agent 状态接续，不重复派单。

## 4. 判断继续、通过或退出

每轮完成后，先检查是否满足通过条件；未通过且有可执行的核实或修订动作时，按下面的判据决定要不要开下一轮。需要探索其他解法时，按前述三档分流的条件启用对应档位。

**停止修订只有一个判据：本轮的新发现里，有哪一条会改变实施动作？**没有的，按第 3 节的判别处置完即收口；有的才继续。下面三条是这条判据的操作提示，不单独构成停止或继续的理由：

- **同一决策点被修订两次仍不稳定**：换档（乙档换组件），不加条款。
- **连续两轮没有任何高／中问题被关闭**：冻结去实测，剩余风险写进已知盲区。
- **本轮既找不到可删或可合并的条款，又只能靠新增条款回应新发现**：说明方案已过厚，同样冻结去实测，不继续修。

轮次上限为 10 轮，**只是防失控的兜底，不是可用额度**；达到上限按“预算用尽”退出，不因为还剩额度就继续。“改一版应该就好了”“多数路都判低”都不构成继续的理由。

提前结束与收口不构成通过——通过仍按下面六条判定。

本 skill 将满足全部通过条件称为“收敛”。只有同时满足以下条件，才标“评审通过”：

1. **先回答终局问题：交付的方案能不能让人直接开工，而不用回来问“这里当初为什么这么定”？**列出读者最可能回头追问的 3 个问题（这一步怎么用、当初为什么这么定、哪里不能改），逐条指到决策登记表的编号或盲区条目；指不到的即为未完成，不必再看其余条件。
2. 每条问题（本轮新提出的，以及闭环表里仍未关闭的）都有至少一路给出的“已关闭／未关闭”判定。旧问题由复用路判定；本轮没有复用路时，指定一路接收闭环表，并在记录里写明放弃该路本轮的盲度——旧版本作废时，改为声明旧问题清单随之作废及理由。扫描路对本轮新提出的问题给出位置与依据即可。关闭项附正文位置；“部分关闭”按未关闭计。未关闭项里没有高或中。
3. 每一处沿用旧证据的地方，都注明了原版本与覆盖范围。
4. 每路的限制清单逐条列出本轮未检查的区域；逐条对照后确认，这些区域里没有未关闭问题所在的位置。
5. 拟交付方案没有阻碍实施的未核实项或必需的待用户决策。
6. 交付正文与最终被评正文为同一版本；仅排版、错字或「契约精度修订」差异须注明并确认技术含义不变。

高／中／低计数只作汇总显示，**不作为继续或收口的依据**，也不得为把某路计数刷到 0 而开轮。

通过仅表示：**在已检查范围和现有证据下，未发现尚未解决的阻碍实施问题。** 它不保证没有遗漏，不证明实现、测试或上线已完成。低问题可披露保留；不按多数票或平均分宣布通过。

发生以下情况时，保存当前方案和记录，按未收敛交付，不为达到某个轮数而继续：

- 必需的用户决定、外部证据或访问能力缺失，且无可继续推进的独立工作；
- 有具体依据的争议仍无法解决，当前也没有新证据、可执行核查、修订或可行的替代探索；
- 达到轮次上限；
- 工具恢复次数已用尽，仍无法完成所需独立评审路。

退出时，标明“阻塞／预算用尽／评审未完成”等原因，并列出恢复条件。不要将退出写成通过。如果用户要求等待或停止，优先遵从。

区分当前方案与未采纳的替代候选。**候选本身不阻止通过**，但必须在决策登记表里逐条留痕（采纳／拒绝 + 理由）；未留痕的候选视为未处理，该轮不通过。**例外**：若某候选表明"照当前方案做会白做"（典型是甲档指出当前路线依赖的核心前提不成立），它按缺陷处理，可以直接阻断。采纳候选时，其实施必需条件纳入核查。

## 5. 交付与后续授权

交付时提供以下内容：

- 方案位置或完整正文，以及实施顺序摘要。
- 当前版本、已完成轮数、路数与选路依据、各路状态及高／中／低计数（仅作摘要）。
- 各路的限制清单：本轮检查覆盖了什么、没覆盖什么。
- 决策登记表（哪个选择点选了哪个实现、什么证据会推翻）、未决项、替代解法的选择理由和核查限制。
- 未核实项台账及其处置：哪些转成了实施期必办条目，哪些已代跑核实，哪些仍开放及恢复条件。
- 实现状态：未实施／实施中／已实施。

尚未完成的评审路标“未完成”，不写成“无问题”。

“先出方案”任务到此结束。原任务已授权继续实施，且没有“只出方案／等我确认”等限制时，通过后沿原授权继续，不增加确认环节。未收敛不自动转实施。提交、对外写入和发布仍遵守既有授权边界。

通过后进入实施，若发现需要偏离已评正文：改动涉及核心前提或技术路线，保存新版本并重开一轮；其余偏离（步骤实现细节、局部顺序、等价替换）就地改，并在记录里补一条“实施期偏离：改了什么／为什么／影响哪些验收项”，交一路复核该条。不得以“实施中才发现”为由绕过已评正文的约束，也不得为每条实现细节重开整轮。
