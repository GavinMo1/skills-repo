# 15 · 保存与草稿：改动什么时候才算安全

> **适用**：做自动保存、草稿恢复或冲突处理的表单与编辑器，要判定「什么时候才能显示已保存」、「重试到底重试哪一版」、切项目时在途回包归谁时。
> **本轮不可交付时**：若这一轮只有显式提交按钮、不做自动保存也不做本地草稿与冲突恢复，停下并说明「没有保存状态要区分」，改读 [02-导航与表单](02-导航与表单.md) 的提交与校验部分。
> **读完能判定**：是否区分当前编辑版、发送快照、已确认版三份版本，有没有用一个全局 saving=false 抹平差异；乱序回包时该显示什么；重试按钮的语义、超时后靠什么确认真实结果；离线草稿的文案、按什么维度隔离、存储不可用时怎么降级、恢复时是否先比服务端版本；切项目与离页时回包归谁、beforeunload 是否被当成唯一保护。

## 一、先判

1. **至少区分三份版本**（表见第四节）：当前编辑版、发送快照、已确认版。请求成功只能证明某一版成功，不能证明眼前这一版已经安全。
2. 提交时保存不可变快照，请求返回后只能确认那份快照对应的版本 → 当前内容若又发生变化，应继续显示未保存或安排下一次保存，不能用一个全局 `saving = false` 盖掉差异。
3. 客户端自增版本可以组织本地状态，但不能单独阻止服务端乱序覆盖 → 更稳妥的起点是每个对象串行保存并合并待发送的新修改，或让服务端支持条件更新、版本校验。即使忽略旧回包，也不代表旧请求没有在服务器最后执行。
4. **自动保存不是每敲一个字就请求**：可以短暂防抖、失焦时保存或显式提交，输入值仍立即更新；IME 组合中避免保存中间候选；校验未通过时说明“尚未保存：请修正日期”等原因，不要静默停止自动保存。
5. 撤销到已确认内容可能让表单重新变干净，所以“是否有改动”既要有版本记录，也要按业务定义比较内容——不要靠每次敲键就永久置 `dirty = true`。
6. **失败后重试哪一版**：重试按钮应明确是“保存当前内容”，还是“重试刚才那次任务”。网络错误后用户可能又修改了内容 → 编辑表单通常需要保存最新有效内容；付款、发布等业务任务则必须按任务身份确认结果，不能随手换成新请求。
7. 超时存在结果未知的情况 → 幂等键、版本号和查询接口帮助确认服务器是否已处理；按钮禁用只能减少本页重复激活。
8. 保存失败不要清空表单，也不要用成功色显示“草稿已存本地”来伪装远端保存成功。
9. **草稿能恢复，不代表已经同步**：离线草稿要明确写“仅保存在此设备，尚未同步”，按用户和对象隔离，记录内容版本、保存时间与来源；存储容量不足、隐私设置或存储不可用时应给出降级——敏感内容是否允许本地存储，按实际产品要求决定。
10. 恢复时比较服务端版本与草稿基线：服务端没变，可以提供恢复草稿；已经变了，就提示冲突并允许查看或选择内容。不能拿时间较新的本地草稿不加判断地覆盖远端。
11. 双标签页、其他设备和其他成员修改，都可能发生冲突 → 服务端返回冲突时保留本地编辑，说明远端已有更新，提供比较、重新加载或有权限的覆盖入口；刷新不能是唯一解决方案。
12. **切项目与离开页面**：从项目 A 切到 B 时，A 的在途回包不能把 B 标成已保存，更不能把 A 的内容写进 B。请求与草稿都应绑定用户、对象与版本；组件卸载只是生命周期变化，不会自动撤销已经送达的业务操作。
13. 有未保存内容时，可在应用内导航中提供保存、保留草稿或放弃的选择，浏览器关闭提示只作补充：`beforeunload` 移动端等场景并不可靠，也不适合承诺异步保存一定完成。应在编辑过程中维护恢复能力，而不是把全部希望放在关页前一刻。

## 二、做完的标准

- [ ] 制造一次慢请求：输入 A 并保存，请求未完成时改为 B；A 返回后应显示“较早版本已保存，当前仍未保存”，再保存 B 才显示当前内容已保存。
- [ ] 再让请求失败一次，确认重试按钮保的是“当前内容”还是“刚才那次任务”，且表单内容没有被清空。
- [ ] 三份版本在代码与界面上都能分开，没有用一个全局 `saving = false` 抹平差异。
- [ ] 在项目 A 有未保存内容时切到 B，确认 A 的回包没有把 B 标成已保存，也没有把 A 的内容写进 B。
- [ ] 断网时草稿文案写明“仅保存在此设备，尚未同步”，恢复前先比对了服务端版本。
- [ ] 生产环境单独验证过：乱序服务端写入、冲突、本地草稿恢复、鉴权与幂等。

## 三、依据与数值

- 防抖时长、草稿隔离维度（用户 / 对象 / 版本）属于项目起点，不是标准要求，本篇不给推荐数值。
- `ETag` / `If-Match` 的条件更新与 `beforeunload` 都是平台提供的机制（HTTP 语义、浏览器事件），可用性随环境变化，不能当成保证。
- `saving = false`、`dirty = true` 是示例代码形态，用来说明“一份全局状态装不下三份版本”，不是接口约定。

## 四、控件、表格与示例

| 版本 | 含义 |
|---|---|
| 当前编辑版 | 用户眼前正在编辑的内容 |
| 发送快照 | 某次请求真正带走的内容与版本 |
| 已确认版 | 服务端明确接受的内容与版本 |

一次保存的完整走向：

```text
输入新版本 → 标记未保存 → 等待保存时机
无在途请求且数据有效 → 发送当前快照
请求成功 → 确认该快照
  当前编辑版仍等于确认版 → 显示已保存
  当前编辑版更新 → 继续保存新快照
请求失败 → 保留编辑内容与未保存状态，提供重试
```

## 五、失败长相与边界

- **输入 A 后改成 B，A 的请求返回就显示“已保存”** → 把“某个快照成功”当成了“眼前这一版已安全”，用户据此关页就丢掉 B。
- **一个全局 `saving = false` 盖掉差异** → 在途请求与当前编辑内容没有分开跟踪。
- **保存失败后表单被清空** → 失败路径没有保留编辑内容与未保存状态。
- **“草稿已存本地”用成功色显示** → 把本地存储伪装成远端保存成功。
- **切到项目 B 后，A 的慢回包把 B 标成已保存** → 请求没有绑定用户、对象与版本。
- **把 `beforeunload` 当成唯一保护** → 移动端等场景不可靠，异步保存也不保证完成。
- **边界**：刷新不能作为冲突的唯一解决方案；服务端已变时不能让较新的本地草稿自动胜出；组件卸载只是生命周期变化，不会自动撤销已经送达的业务操作；内存中的模拟服务端没有持久化也没有真正的网络，它的状态正确不能代替后端契约正确。
