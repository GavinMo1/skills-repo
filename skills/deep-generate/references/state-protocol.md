# 状态协议

首次登记、派发评审或恢复任务前读取。协调者维护唯一当前清单，正文、报告和历史快照保存事实依据。当前格式为版本2，不兼容直接套用版本1。

## 日常记录

最小示例仅说明字段，不是真实执行记录：

```json
{
  "schema_version": 2,
  "run_id": "example-run",
  "next_action": "收取章节初稿",
  "revision_limit": 2,
  "actors": {"writer": {"identity": "实际执行实体身份"}},
  "files": {
    "ch01": {
      "path": "01-标题.md", "kind": "chapter", "sha256": null,
      "owner": "writer", "contributors": [], "revisions": []
    }
  },
  "reviews": [],
  "reading": {"status": "计划中", "reason": "连续学习", "review_ids": []}
}
```

- 路径相对主题根目录，使用 `/`，解析后不得越界。文件 ID 保持稳定；改名只更新路径。
- `kind` 为 `chapter`、`guide`、`source` 或 `shared`。SHA256 对磁盘实际字节计算；未产出文件为 `null`。哈希只标识版本，不证明内容正确。
- `owner` 必须存在，未分配可为 `null`。`actors` 保存环境可核实的实体身份；未知为 `null`，不以角色名证明独立性。
- `contributors` 保留全部实际作者和修改者，每项为 `{"actor":"writer","sha256":"实际输出哈希"}`，必须包含当前产出版本。负责人变更不清空历史。协调者修改正文也要登记。
- `revisions` 只记录实际完成的问题修订，每项为 `{"id":"fix-01","output_sha256":"实际输出哈希","record":"_work/run/处理/fix-01.md"}`。处理记录说明问题 ID、修改前后版本和处理结果。相同提交续接更新原项，不重复登记；正常整合不计问题修订，但其修改者与输出仍登记在 contributors。
- `revision_limit` 默认2，可按用户指示调整。剩余轮次从实际修订条目计算，不人工另存计数；历史不明时 `revisions` 为 `null`，不能假定还有预算。

未产生修改时不计轮次。问题只经证据撤销、没有正文修改时，在评审报告解释，不新增修订项。预算耗尽不影响报告真实问题，也不允许自动通过。

## 评审记录

每项包含 `id`、`kind`（`content` 或 `reader`）、`actor`、`report`、`coverage`：

```json
{
  "id": "review-01", "kind": "content", "actor": "reviewer",
  "report": {"path": "_work/run/评审/01.md", "sha256": "实际报告哈希"},
  "coverage": [{
    "target": "ch01", "status": "通过", "scope": "本章及共享约定",
    "inputs": [{"file_id": "ch01", "sha256": "实际输入哈希"}],
    "issues": [], "applicability": "current"
  }]
}
```

内容状态为通过、待修订、待核实、未评审；读者状态为已完成、部分覆盖、未完成。`issues` 记录未解决的高、中问题以及影响必要判断的核实项 ID，低影响建议留在报告；通过记录的 `issues` 必须为空。

`scope` 写实际检查范围。输入必须包含目标与影响判断的共享或相邻材料；不能只因目标哈希未变就忽略依赖变化。`applicability` 为 current、pending 或 historical：输入改变后先标 pending，独立评审者确认沿用或复查后新建当前记录，旧记录留为历史。

评审前保存目标及必要输入的可恢复版本，可用不可变副本、Git 提交或等效版本存储；报告记录具体定位。需要文件快照时，可在 inputs 条目加 `snapshot` 相对路径，脚本核对其哈希。并发、异步交付、恢复或审计需要精确冻结输入时必须登记 snapshot；不要求每次判断重复复制已有相同版本。

当前评审者不能是目标的实际作者或修改者。首评用新上下文，不提供旧判断；身份登记只能检查实体是否重合，不能证明上下文已隔离或评审真实独立。

## 试读与交付

`reading.status` 为计划中、已完成、部分覆盖、未完成或跳过；reason 说明路线及覆盖限制或跳过原因，review_ids 引用当前适用的读者报告。全部完成须由对应范围的已完成报告支持，部分覆盖不能声称全读。

交付前运行只读脚本，要求 Python 3.9 或更新版本：

```text
python <本技能目录>/scripts/check-state.py --root <主题目录> --state <清单路径> --final
```

退出码0表示已实现的机械检查无失败或未检查项；1表示失败；2表示存在未检查项。非 final 模式用于恢复和中途核对。报告、引用内容、范围完整性、上下文隔离、来源真实性和链接锚点仍需实际检查。

## 并发、恢复与迁移

协调者派发修改前，记录涉及文件、输入版本、执行实体和占用情况，可放在现有任务说明中；同一文件只允许一个修改者。恢复后先查任务是否仍运行，不重复派发。不要求在总清单与处理文件中提前登记同一修订轮次。

清单更新采用同目录临时文件，成功解析后替换，保留上一有效版本。损坏时对照实际正文、运行任务、报告和版本记录恢复；无法确认的身份或历史标未知，不能凭空补全。需要严格审计时补充实际输入快照与版本定位，不为普通任务增加多份人工账本。

迁移版本1时保留原清单，按实际输出重建 contributors 与 revisions，取消纯派发或失败所占轮次，保留实际修订。重建评审输入及有效性，核对后再使用版本2；不能只修改 schema_version。历史无法核实则保留未知和交付限制。
