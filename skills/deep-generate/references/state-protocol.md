# 状态协议

首次登记、派发评审、恢复任务或交付前读取。任务状态清单 `_work/<任务标识>/任务状态.json` 是唯一当前状态；正文、报告与版本快照保存事实依据。协调者维护清单，执行者只提交正文与报告。

`--root` 一律指**账本所在 `_work` 目录的父目录**（即主题目录）。root 取值不同会改变路径解析结果，机械检查的结论随之不同，不得随意更换。

## 格式版本与版本门

清单必须带 `"schema_version": 2`。`check-state.py` 与 `state.py` 共用同一个判据（模块级函数 `v2_ok`，判据为 `type(...) is int and == 2`）。

- **拒绝**：缺失该字段、或为 `1`／`3`／`"2"`／`2.0`／`true`，`state.py` 全部命令 rc=1 并提示「需要版本2；旧版须依据历史迁移」。
- **能力边界**：版本号匹配**不证明**已完成迁移。迁移是人工义务，检查器不能核验。
- **覆盖范围**：入口门只覆盖版本门。`freeze` 因此**不跑完整机械检查**——在 `failed` 非空的账本上 `freeze` 仍可能成功并写盘。其余命令在写盘前跑一次完整检查。

## 谁能用哪条路

- **工具路径**：`scripts/state.py` 的 8 个子命令（下文「工具操作」）。
- **手工路径**：手工编辑清单**仅限** `path` 与 `revisions` 的历史恢复；`actors`、`contributors`、评审结论、各类计数**不得**手改——那些改动会让机械门与独立性检查失真（见「已知局限」）。
- 任何手工编辑后都必须通过 `check-state.py`。
- `actors[].identity` 是**自由文本**，机械层只能判断「是否相等」，不能证明身份真实或上下文隔离。`review` 要求参与评审的执行实体身份可核实：身份为 `null` 时拒绝登记，作者侧身份为 `null` 时同样拒绝，并分别提示是评审者侧还是作者侧的问题。
- `kind` 一旦登记**不可变更**（`register` 拒绝改类型，同路径换 ID 也被拒）。`chapter`／`guide` 是交付内容，`source` 是依据材料（同样需要内容评审），`shared` 不参与交付门槛判定。登记前选对 type；选错只能重建任务。
- `register` 会改写 `owner`，并把当前执行实体追加进 `contributors`——这是**署名动作**，不是单纯的元数据更新。
- **退出码语义只属 `check-state.py`**：0 = 无失败且无未检查项，1 = 有失败，2 = 有未检查项。`state.py` 是 0 成功／1 拒绝／2 命令行用法错误。
- **写前自检 ≠ 可交付**：写命令跑的是非 final 检查，因此存在「写命令全部成功、`--final` 非 0」的状态。零信号不代表账本无缺陷。

## 工具操作

需要 Python 3.9 或更新版本，仅使用标准库。所有命令都传 `--root <主题目录>` 和 `--state <清单路径>`，其他文件参数使用主题根目录内的相对 `/` 路径。

```text
python state.py --root <主题目录> --state <清单路径> init --run-id <任务标识>
python state.py --root <主题目录> --state <清单路径> actor --id writer --identity <实际执行实体身份>
python state.py --root <主题目录> --state <清单路径> register --id ch01 --path 01-标题.md --kind chapter --actor writer
python state.py --root <主题目录> --state <清单路径> freeze --files ch01 shared --output _work/run/评审/首轮输入.json
python state.py --root <主题目录> --state <清单路径> review --spec _work/run/评审/首轮登记.json
python state.py --root <主题目录> --state <清单路径> reading --status 已完成 --reason <实际阅读范围> --reviews reader-01
python state.py --root <主题目录> --state <清单路径> next --text <下一步动作>
python state.py --root <主题目录> --state <清单路径> register-batch --spec <批量参数.json>
```

- `init` 创建清单并写入 `schema_version`；已有清单时拒绝覆盖。默认问题修订预算为 2，可用 `--revision-limit` 指定。
- `actor` 登记可核实的执行实体身份；已登记身份不能改写，实际身份不同请用新 ID。
- `register` 在正文产出后计算哈希、保存内容快照并保留作者/修改者历史。每次修改后重新执行；依赖变化输入的当前评审自动转 `pending`，已完成试读转未完成。
- `register-batch` 一次登记多份被同时修改的文件，避免中间状态仍有其他哈希过期。参数是非空数组，每项含 `id`、`path`、`kind`、`actor`，问题修订项另含 `revision`、`record`；整批通过检查才更新清单。空数组或空对象一律拒绝。
- 问题修订完成后，在 `register` 增加 `--revision <修订ID> --record <处理记录路径>`；同一修订续接沿用 ID。普通写作与跨章整合不加这两个参数。没有新内容不计轮次；预算耗尽时拒绝新增修订，不改称整合来绕过。
- `freeze` 的文件 ID 必须已登记，且包含目标及必要的共享/相邻材料。工具生成不可覆盖的输入凭据（含哈希与快照路径），把凭据与快照交给评审者；复评使用新的输出文件名。
- `review` 读取提交格式，自动关联冻结输入并计算报告哈希。当前输入的新评审把同类、同目标的旧覆盖转 `historical`；输入不匹配的只记 `pending`。工具不判断报告论证、范围是否充分或上下文隔离。
- `reading` 登记主路线实际覆盖；完成或部分覆盖须引用当前适用的读者报告。工具不能从文件数量推断已完整阅读。
- 提交参数与冻结凭据只作单次操作依据，不维护当前结论。命令先校验再写入，错误时保留当前清单。

## 手工维护的合法条件

只有三种情形允许手工编辑清单，且都必须随后通过 `check-state.py`：

1. 修正 `files[].path`（路径变更）；
2. 恢复 `revisions` 的真实历史（原值丢失时补回真实记录，不得编造）；
3. 为**版本1账本**补 `schema_version: 2`（仅当其余字段已合规、机械检查无失败）。

手工编辑后，在 `交付状态.md` 记明：改了哪个字段、为什么、核对结果。**不要**用占位字符串顶替未知身份——机械门会把它当作已核实身份，从而放行一份独立性未经核实的交付。

## 日常记录

清单由工具生成或按上节手工修正；以下字段用于核对记录，不需要手算哈希。

- 路径相对主题根目录，使用 `/`，解析后不得越界。文件 ID 保持稳定；改名只更新路径（见「改名是审计事件」）。
- `kind` 为 `chapter`、`guide`、`source` 或 `shared`。SHA256 对磁盘实际字节计算；未产出文件为 `null`。哈希只标识版本，不证明内容正确。
- `owner` 必须存在，未分配可为 `null`。`actors` 保存环境可核实的实体身份；未知为 `null`。
- `contributors` 保留全部实际作者与修改者，每项 `{"actor":"writer","sha256":"实际输出哈希"}`，必须包含当前产出版本。负责人变更不清空历史。
- `revisions` 只记录实际完成的问题修订，每项 `{"id":"fix-01","output_sha256":"…","record":"_work/run/处理/fix-01.md"}`。处理记录说明问题 ID、修改前后版本与结果。相同提交续接更新原项；正常整合不计问题修订，但修改者与输出仍登记进 `contributors`。
- `revision_limit` 默认 2。剩余轮次从实际修订条目计算，不人工另存计数；历史不明时 `revisions` 为 `null`，不能假定还有预算。
- 未产生修改时不计轮次。问题只经证据撤销、没有正文修改时，在评审报告解释，不新增修订项。预算耗尽不影响报告真实问题，也不允许自动通过。

## 评审记录

保留原始 Markdown 报告；协调者按报告整理提交参数 JSON，再执行 `review --spec`。下例只说明格式：

```json
{
  "id": "review-01", "kind": "content", "actor": "reviewer",
  "report": "_work/run/评审/01.md",
  "inputs": "_work/run/评审/首轮输入.json",
  "coverage": [{
    "target": "ch01", "status": "通过", "scope": "本章及共享约定",
    "issues": []
  }]
}
```

内容状态为通过、待修订、待核实、未评审；读者状态为已完成、部分覆盖、未完成。`issues` 记录未解决的高、中问题以及影响必要判断的核实项 ID；通过记录的 `issues` 必须为空。

`scope` 写实际检查范围。输入必须包含目标与影响判断的共享或相邻材料；不能只因目标哈希未变就忽略依赖变化。

**`applicability` 的两步迁移**：输入改变后，旧覆盖先转 `pending`；由独立评审者确认沿用或复查、并以**匹配输入登记新记录**后，旧记录才转 `historical`。只完成第一步不算清理——`pending` 会一直计入未检查项。

评审前用 `freeze` 保存可恢复版本，报告记录具体定位。快照在清单的 `inputs` 中登记 `snapshot` 路径，检查脚本核对其哈希。不能为消除待核实状态，把旧报告重新登记为新检查。

当前评审者不能是目标的实际作者或修改者。首评用新上下文，不提供旧判断。

## 试读与交付

`reading.status` 为计划中、已完成、部分覆盖、未完成或跳过；`reason` 说明路线及覆盖限制或跳过原因，`review_ids` 引用当前适用的读者报告。全部完成须由对应范围的已完成报告支持；部分覆盖不能声称全读。`跳过` 只免除试读本身，**不能**替代「读者报告已失效」所需的复评；`--final` 为 0 也不代表做过试读。

**机械门**：交付前运行只读脚本

```text
python <本技能目录>/scripts/check-state.py --root <主题目录> --state <清单路径> --final
```

**`--final` 退出码 0 才算机械门通过**。退出码 2 表示存在未检查项，1 表示有失败。非 final 模式只用于恢复与中途核对。

**完整判定 = 机械门 + 协调者签署**：交付说明必须写明是否走过手工绕过、是否有无法清零的条目、是否归档处理过。这一项没有机械钩子，只能靠披露。

### 九条未检查项与清法

`--final` 的未检查项共九条消息，逐条对应如下清法：

| 未检查项 | 清法 |
|---|---|
| `缺少当前内容通过记录` | 由独立评审者以匹配输入登记 current 通过评审 |
| `当前内容尚无通过结论` | 同上；新评审把同目标同 kind 旧条目转 `historical`，两条一起消失 |
| `评审适用性待确认` | 以匹配输入登记新记录（确认沿用也要登记）；复评须覆盖旧记录全部目标 |
| `试读未完成或仅部分覆盖` | 完成试读，或用 `reading --status 跳过` 并写理由 |
| `实体身份未知` | `owner` 侧：`register --actor <真实可核实身份ID>` 可消掉本行，但该命令会把此 ID 记为当前版本贡献者（署名断言），只能在该 ID 确为本版本作者时采用；`contributors` 侧：工具路径无合规修复 |
| `无法核实实体是否重合` | 评审者侧换可核实身份重做；作者侧不可核实则本行常驻 |
| `尚未产出或登记版本` | 产出后 `register`；不再产出时按「存量失效账本」归档 |
| `未分配负责人` | `register --actor`（会改写 `owner`） |
| `修订历史缺失或未知` | `revisions: null` 无工具修复路径（`register` 保留 `null`、`--revision` 硬拒）；只能补真实历史或归档 |

**分层，勿混**：新账本交付前必须清零九条；含 `revisions: null` 或「已登记但不再产出」的条目时，**不存在同账本清零路径**，唯一合法出路是按「存量失效账本」归档，或重建任务。

**删除不属于维护路径**。工具没有删除命令，协议也不提供删除规则：删条目再换 ID 重登记会抹除真实作者记录；「确认废弃」式的删除必然减少 `files` 计数并连带破坏指向它的评审；删后 `register` 还会因悬空引用报错。需要停用条目时走归档。

## 并发与恢复

同一账本同一时刻只运行一个 `state.py` 写命令。协调者派发修改前，记录涉及文件、输入版本、执行实体和占用情况，可放在现有任务说明中；同一文件只允许一个修改者。恢复后先查任务是否仍运行，不重复派发。

**跨机/跨会话交接**：在交接点各跑一次 `check-state.py --final`（记退出码）与交接指纹脚本，两次不一致即说明对方改过账本。指纹覆盖 `schema_version`、`files` 的路径/哈希/负责人、评审报告的路径与哈希、覆盖的目标/适用性/结论/问题/输入、以及 `actors` 身份。**指纹相等只证明这些字段未变，不证明账本未被编辑。**

工具通过同目录临时文件更新清单，成功解析后替换，并保留 `.previous.json`。该文件只有**一代**，下一次成功写入即被覆盖，不能当版本历史用。损坏时对照实际正文、运行任务、报告和版本记录恢复；无法确认的身份或历史标未知，不能凭空补全。

## 独立规则：存量失效账本

> **命中下列任一判据的账本，不得执行任何 `state.py` 写命令。**
>
> 1. `check-state.py` 在 `files.<id>` 条目上报「实际文件哈希与登记不符」；
> 2. 某个 `files[].path` 在磁盘上不存在；
> 3. 某个 `coverage[].inputs[].snapshot` 缺失，或归一后与登记值不符（仅换行符差异不算失效）；
> 4. 某个 `reviews[].report.path` 不存在，或归一后与登记值不符。
>
> **唯一例外**：判据 3／4 成立、但正文未变（登记哈希与当前正文相符）时，允许 `freeze` 重建快照并重做评审——前提是 `freeze` 不报「已有快照损坏」。其余情形一律归档。

理由：`register` 按当前字节重算哈希，会把真实改动一并登记；它还会经 `invalidate()` 把 `current` 评审转成 `pending`；失败的批次会在 `版本/` 留下无引用快照。

## 存量诊断与处置

诊断只用于定性，不产生写动作。归一化口径：去 UTF-8 BOM、`\r\n` 与孤立 `\r` 归一为 `\n`、保留末尾换行差异。

1. `files[].path` 存在：登记哈希与当前字节相符 → 正文未变；不符 → 与 `版本/<登记 sha>/` 下的文件比较（两边同口径归一），相等即「换行符漂移」，不等即「内容已变」。
2. `files[].path` 不存在：请协调者指出新路径（若存在）。新路径归一后与登记哈希相符 → 内容未变，属路径变更；否则按「内容已变」。
3. 新路径无从确定，或 `版本/<登记 sha>/` 不存在 → **无法证明** → 按「内容已变」处理并披露。

**改名是审计事件，不是轻量修复**：`register --path` 会重写哈希、改写 `owner`、追加 `contributors`，并把相关 `current` 评审转成 `pending`——「只改路径」在工具层不存在，改名后必须重做评审。成本如实计入；不愿意承担就归档。

**处置**：按归档处理，在 `交付状态.md` 写明受影响章节、失效锚点按 `files`／`report`／`inputs` 的分类计数、可用性结论，以及是否走过手工绕过。要复活＝重做。

## 快照的限制

`版本/<哈希>/<文件名>` 位于**账本所在目录**（不是 `--root/版本/`），是字节副本，相同内容复用。

外部工具（同步客户端、编辑器、autocrlf）对本目录做换行符转换后，快照的字节哈希会与其目录名不符，`register` 会报「已有快照损坏」，`freeze` 也无法重建。因此：**不可变副本只在未被外部转换时成立**；需要审计精确冻结输入时，先确认快照与目录名仍自洽。
