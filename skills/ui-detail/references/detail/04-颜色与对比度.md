# 04 · 颜色与对比度：把“看着还行”变成可检查

> **适用**：有人问「这个灰能不能用」「这个按钮文字够不够清楚」，或要拿具体色值核对 AA/AAA、算半透明叠加后的实际效果、给色板分语义层时。
> **本轮不可交付时**：若这一轮要做整套深色主题的表面与强调重排，停下并说明「不止单对颜色」，改读 [05-深色主题](05-深色主题.md)；若要谈焦点外观的面积与前后对比，改读 [07-无障碍](07-无障碍.md)。
> **读完能判定**：一对前景/背景在普通文字、大号文字、必要图形三种对象下是否过 AA 或 AAA；大号文字成不成立、装饰边框与禁用态是否在豁免里；半透明是否先按通道合成；一个色值该叫色板格子还是语义用途；错误与成功是否只靠了红绿；APCA 能否当合规结论。

## 一、先判

1. **对比度是一对颜色的关系**：先确定这对前景与背景，再查门槛；单独一个色号没有“通过 AA”这件事。
2. **检查对象三选一**：普通文字、大号文字、识别 UI 组件与状态所必需的视觉信息与必要图形，三者的门槛不同（表见第四节）。
3. **大号文字要同时看字号与字重**：至少 `18pt`，或至少 `14pt` 粗体，通常换算约为 `24 CSS px`，或 `18.67 CSS px` 粗体；只凭字号判成“大号”会误判。
4. **边框要不要 `3:1`，看它承不承担识别**：填充和文字已能清楚识别按钮时，装饰性边框的适用情况不同；禁用组件有相关豁免，但正常的占位文字、辅助说明不能用“次要”作为不达标的理由。
5. **焦点不是一个孤立的“3:1”数字**：AA 要求焦点可见、且不被作者内容完全遮挡；AAA 的 Focus Appearance 另有面积与聚焦前后对比要求，本篇不展开（见第五节）。
6. **半透明先合成再判定**：对普通 sRGB 页面中的不透明底色，先按通道近似合成 `C = α × 前景 + (1−α) × 背景`，再用最终颜色算对比度。
7. **`rgba()` 还是 `opacity` 先分清**：`rgba()` 只改变指定颜色的透明度；`opacity` 影响整个元素及子树的合成结果——卡片整体半透明时，文字也会被一起削弱。
8. **有渐变、图片、多层透明或其他色彩空间时，按实际渲染取样**，检查文字经过的较差背景区域；只算 CSS 里声明的两个色值可能失真。
9. **先分清一个色值是色板格子还是语义用途**：`gray-600` 是色板格子，`text-secondary` 是“次要文字”的语义；组件使用后者，切主题时再为语义映射不同值。
10. **错误和成功状态要配图标或文字**，不能只靠红绿；hover、pressed、selected、focus 也要分别检查——状态覆盖层能统一算法，不能自动保证每个状态都达标。
11. **APCA 不能当合规结论**：APCA 会考虑文字极性等因素，输出的 Lc 与 WCAG 2.x 比值不是同一单位，使用建议还涉及字体大小和字重；本篇以 WCAG 2.2 作为明确的核查基线，不用 APCA 替代其合规判定。
12. **色域不背全部责任**：普通 hex 色值通常表示 sRGB，Display P3 要显式使用对应颜色表示法；同一个 hex 在不同屏幕上观感有差异，也涉及校准、亮度和环境。

## 二、做完的标准

- [ ] 每个要用的组合都记成「哪个前景在什么表面上」，覆盖默认、悬停、选中、错误和聚焦状态，浅色与深色主题各一份。
- [ ] 每个比值可复算：自己把通道线性化算一遍，结果与记录一致；不把 4.49 向上显示成 4.5 后算通过，也不只贴门槛配色，给状态变化留余地。
- [ ] 半透明前景在做判定前已按通道合成成最终颜色；渐变、图片、多层透明的位置按实际渲染取样过。
- [ ] 组件里引用的是语义名（`text-secondary`），不是色板名（`gray-600`）。
- [ ] 大号文字的那一处同时记了字号与字重两个条件。
- [ ] 占位文字、辅助说明、置灰控件逐条确认：是落在禁用豁免里，还是确实不达标。
- [ ] 每个状态变化除了红绿之外还有一条通道（图标或文字）。

## 三、依据与数值

- **标准要求**：第四节第一张表整张来自 WCAG 2.2——普通文字、大号文字、识别 UI 组件与状态所必需的视觉信息与必要图形，三类对象各自的 AA / AAA 门槛都是标准要求，完整适用条件见原文（非文字对比度那一行 AAA 不另设更高数值）。
- **标准要求**：“大号文字”指至少 `18pt`，或至少 `14pt` 粗体；通常换算约为 `24 CSS px`，或 `18.67 CSS px` 粗体。
- **示例值**：第四节的色对、近似比值，以及 `87%` 白叠加在 `#121212` 上每通道约 224 即 `#E0E0E0`，都是项目示例；显示值做了四舍五入。
- **平台约定**：HSL 的明度百分比不等于 WCAG 相对亮度，Material 的 tone 也不能直接当成 HSL 百分比；“浅色用 tone 40、深色用 tone 80”不能推广为任意品牌色的换算公式。

## 四、控件、表格与示例

以下为 WCAG 2.2 的相关门槛摘要，完整适用条件见原文：

| 对象 | AA | AAA |
|---|---|---|
| 普通文字 | 至少 4.5:1 | 至少 7:1 |
| 大号文字 | 至少 3:1 | 至少 4.5:1 |
| 识别 UI 组件与状态所必需的视觉信息、必要图形 | 与相邻颜色至少 3:1 | 不另设更高数值 |

把每个 8 位 sRGB 通道除以 255 得到 `c`，再线性化：

```text
c ≤ 0.04045：c_linear = c / 12.92
其他：c_linear = ((c + 0.055) / 1.055) ^ 2.4

L = 0.2126 R_linear + 0.7152 G_linear + 0.0722 B_linear
contrast = (较亮 L + 0.05) / (较暗 L + 0.05)
```

| 前景 / 背景 | 近似比值 | 普通文字 AA |
|---|---|---|
| `#1F1F1F` / `#FFFFFF` | 16.48:1 | 通过 |
| `#595959` / `#FFFFFF` | 7.00:1 | 通过 |
| `#767676` / `#FFFFFF` | 4.54:1 | 通过 |
| `#8C8C8C` / `#FFFFFF` | 3.36:1 | 不通过 |
| `#E0E0E0` / `#121212` | 14.19:1 | 通过 |

把颜色按用途命名——色板格子与语义用途分两层：

| 原始色 | 语义用途 | 组件用途 |
|---|---|---|
| `gray-950` | `text-primary` | `dialog-title` |
| `blue-700` | `action-primary` | `button-primary-bg` |
| `red-700` | `text-danger` | `field-error` |

## 五、失败长相与边界

- **只拿一个色号问「这个灰能不能用」** → 对比度是一对颜色的关系，缺背景就没有判定对象。先补上它落在什么表面上。
- **4.49 被显示成 4.5 后判通过** → 判定用了四舍五入后的显示值。按未取整的值判，并给状态变化留余地。
- **半透明前景直接按声明色比值判通过** → 没有先按通道合成。合成后重新算，渐变或多层透明的位置按实际渲染取样。
- **红绿一对颜色表状态，色弱用户看不出** → 状态只靠色相。补图标或文字。
- **切主题后语义色全错位** → 组件直接引用了色板格子，没有经过语义层。
- **把 tone 40 / tone 80 当通用换算公式套到品牌色上** → HSL 明度与 Material tone 都不等于 WCAG 相对亮度，要按实际色值复算。
- **边界**：不是所有边框都必须 `3:1`；装饰性边框不承担识别、禁用组件有豁免——但占位文字与辅助说明不在豁免里。焦点面积的完整要求在 [07-无障碍](07-无障碍.md)。APCA 的 Lc 不能替代 WCAG 2.2 的合规判定；同一个 hex 在不同屏幕上观感不同，不能全归因于色域。
