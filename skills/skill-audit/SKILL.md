# Skill 审计

读用户的 skill（SKILL.md 和它的 references），按文末判据列出可优化点。

**输出粒度**：一条一个点，一句话说清哪里不对、该怎么改。不写行号、小节或文件定位，不逐句复述原文，不列前后对比表。

**任务到清单为止**：不改文件、不执行或调用被审的 skill、不派子 agent、不跑测试。用户看完清单、另行要求修改时才动手。

**用户没指明是哪个 skill 时，先问是哪一个**，不要自己扫 `~/.agents/skills` 挑一个来审。

# 判据：Skill 优化心得

> 一句话：把 skill 当作帮助 Agent 作出判断、完成任务的工作机制，而不是一份"要求越多越好"的提示词。
> 由此推出默认提问方式：不问"还缺什么规则"，而问"这条规则让 Agent 怎样判断、判断得对不对"。

## 一、先分清两个层面

同一条指令可以从两个层面改，效果完全不同：

| 层面 | 关注的问题 | 典型改动 |
| --- | --- | --- |
| **表达层** | AI 能不能准确理解这条要求？ | 消除歧义、统一术语、明确动作与条件 |
| **机制层** | 这条要求本身是否合理？它会让 AI 怎样开展工作？ | 调整决策依据、执行顺序、证据要求、停止条件、反馈方式 |

表达层是必须过的关，但**只改表达层经常不够**。原指令说得再清楚，也可能让 Agent 走上错误的路径——这时要靠机制层改写，也就是换掉它判断"做完了没有"的依据。

## 二、六个考察问题

一套 skill 的规则，最后都能落到这六个问题上。

### 1. 它到底要帮助用户得到什么？

先保留目标，再判断规则是否有用；每条规则都要问一句"它是否在帮助达成这个目标"。

反例：项目面经要挖掘的是贡献，不能为了"避免包装"就把它改成事实摘录工具——目标被规则挤掉了。

### 2. 每条要求为什么存在？

把字数、数量、格式这类表层要求还原成背后的目的，再直接定义需要覆盖的内容。

"需要的是解释充分、没有废话"和"统一长短"是两件事；前者可以用，后者只会制造凑字数。
同理，"要求少说废话"这类否定式规则，更有效的写法是定义**哪些内容必须说、哪些内容没有价值**。

### 3. Agent 在关键分岔处知道怎么选吗？

真正有价值的指令往往不在"要做得多好"，而在这些选择上：

- 什么时候追问，什么时候直接解释
- 什么时候继续查证，什么时候停止探索
- 什么时候复查，什么时候部分交付

分岔点没有指令，Agent 就只能自己猜；猜出来的行为不稳定，也无法复现。

### 4. 结论有没有超出证据？

区分事实、推断、假设。几类高频越界：

- 文本依赖 ≠ 用户缺口
- 源码能力 ≠ 个人贡献
- 模拟试读 ≠ 真实体验
- 脚本通过 ≠ 内容正确

### 5. 严谨性的成本值得吗？

检查要针对**实际的失败风险**，不能只增加流程。

- 值得保留：独立评审（真正引入了外部视角）
- 未必值得：重复账本、默认评分、机械多轮（成本确定，收益不确定）

### 6. 规则能否被准确执行并持续维护？

术语一致、条件明确、动作具体、完成标准可检查；详细分支放进 `references/`，同一规则只维护一处。

这是中文语境吸收 STE 原则的重点：可执行、可维护，而不是写得更"规范"。

## 三、贯穿整个会话的方法

**先理解现有设计想保护什么，再决定保留、改写、删除或补齐。**

不要因为个人偏好、某一次失败或某一个场景，就直接把一条局部经验升级成所有任务的通用规则。

## 四、两个最容易漏掉的执行细节

### 1. 挪进 `references/` 的细节，有没有在分岔点被真正要求读？

挪出去只是第一步。还要在走到那个分岔点时写明：

- 此时**必须完整读完**哪个文件
- 此时**不要加载**哪些文件

否则引用文件永远躺着没人看——挪出去却不给触发条件，等于把内容藏起来。
反过来，每次任务都必读的内容不要拆进 `references/`：读取条件相同，拆开只多一次读取、一个断链风险，省不下 context。

### 2. 约束强度和出错代价匹配吗？

判据只有一句：**Agent 做错了，代价有多大。**

- 代价是"结果平庸"（创作类）→ 给原则，不给步骤。给步骤只会得到模板化结果。
- 代价是"一处错就毁"（改文件格式这类操作）→ 给死脚本，不许改参数。

## 五、案例：从表达层走到机制层

### 案例 1：字数要求

原指令：

> 每个面试回答不少于 150 字。

- **表达层优化**：把"回答"指代清楚、"字数如何统计"写清楚。指令更明确了，但仍然会诱导 AI 凑字数。
- **机制层优化**：继续追问"为什么要 150 字"。如果目的是回答充分，就改为：

> 主问说明必要背景、个人职责、关键行动和结果；追问直接解释所问机制，只在必要时补充背景。

这不是换措辞，而是**改变了 AI 判断"回答是否完成"的依据**。

### 案例 2：追问要求

> 不断追问，直到用户理解。

即使写得毫无歧义，仍可能低效。需要进一步规定：什么时候直接解释、什么问题值得追问、凭什么判断"理解了"、什么时候停止。

判据同样来自第 3 个问题——分岔处有没有可执行的指令。

## 六、一页检查清单

按顺序过一遍：

- [ ] 目标写清楚了吗？现有规则有没有把目标挤掉？
- [ ] 每条规则能说出"为什么存在"吗？说不出就还原目的后重写。
- [ ] 追问／解释／查证／停止／复查／部分交付，这些分岔点有指令吗？
- [ ] 结论的证据边界写了吗（依赖≠缺口、源码≠贡献、试读≠体验、跑通≠正确）？
- [ ] 新增的严谨性流程，针对的是真实失败风险吗？
- [ ] 术语一致、条件明确、完成标准可检查吗？同一规则是否只维护一处？
- [ ] `references/` 的每个文件，都在分岔点写了强制触发条件吗？
- [ ] 每条约束的强度，与做错的代价匹配吗？
- [ ] 是否在保留现有设计的前提下改动，而不是把一次失败升级成通用规则？
