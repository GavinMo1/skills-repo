# ui-detail `references/detail/` 调整标准 v1

这份文件是调整 `skills/ui-detail/references/detail/` 下 17 篇的唯一依据。子 agent 的任务书**只指路径、不转述内容**；拿不到这份文件就停下并说「缺标准」，不要凭印象动手。

---

## 0. 适用范围

| 对象 | 是否适用 |
|---|---|
| `references/detail/01-浮层.md` … `17-拖拽与排序.md` | 适用 |
| `references/index.md`、`references/stage/**`、`SKILL.md`、`README.md`、`scripts/check-links.py` | **不适用**，主会话独占（见 §9） |

调整的是**形态**：让一个带着具体任务来查的 agent，读三四十行就能判断、能交付。不是重写内容，不是润色文风。

---

## 1. 为什么原文照搬不适合当 reference

17 篇的原始读者是**顺次阅读的人**，不是**带着一个任务来查的 agent**。证据在文本形态里，不在内容质量里：

1. **顺序阅读框架**：`[系列目录] · 上一篇：… · 下一篇：…`、`见第 12 篇`、`系列会按实际问题继续扩充`。对查单点的 agent，这些是每次都要跳过的噪点。
2. **劝说性开场**：先摆一个「你可能能写出页面，却说不清该用抽屉还是对话框」的处境，再进正题。agent 没有「被说服」这个动作，它需要的是判据。
3. **散文式铺陈**：连续数段讲一个虚构用户怎么点、怎么改。判定埋在中段，只读前 30 行的 agent 拿不到。
4. **旁支**：`06` 里浏览器 Performance 面板的五步操作（取证工具）、`13` 开头对某个具体页面的免责声明。对「怎么把这个界面做对」没有输入。
5. **同一件事反复自证**：一条边界在三篇里各讲一遍，读者不累，agent 的上下文会累。

**但价值必须一条不丢**：数值三分（标准要求 / 平台约定 / 项目起点）、WCAG 与 APG 的具体门槛与条号、代码片段、"为什么"。这是这套材料比同类 UI skill 强的地方。删形态、不删证据。

一条对主管判断的修正：**「有旁支就删」不足以指导 17 篇**。旁支里常常夹着真判定（`06` 的五步操作里有一句「看到 `getBoundingClientRect()` 不等于每次发生强制布局」）。所以删除规则必须写成「删动作、留判定」，见 §5。

## 2. 固定结构（顺序不可变）

每篇按下列顺序组织。`一`、`二`、`五` 必备；`三`、`四` 本篇没有对应内容时整节省略，不留空节。

```markdown
# NN · <原样标题，编号与标题文字都不许改>

> **适用**：<0.8.1 版原文，一字不动>
> **本轮不可交付时**：<0.8.1 版原文，一字不动>
> **读完能判定**：<可压缩到一行，但判断对象不得减少>
> **超限理由**：<仅当行数 > 110 时出现，见 §3；否则这一行不存在>

## 一、先判

<N 条判定，每条一句，条件是任务里能看见的东西>

## 二、做完的标准

- [ ] <可被第三方打勾的一条>

## 三、依据与数值

<门槛、条号、三分标注>

## 四、控件、表格与示例

<表格、代码块，原样保留>

## 五、失败长相与边界

<症状 → 原因；例外与不该动的场合>

参考：<原链接原样>
```

**为什么「判定在前」**：这个 skill 的预算是「除 `SKILL.md` 外最多 3 篇」。拿到一篇的 agent 通常已经知道要改什么，缺的是「这一处该选哪个、做到什么算完」。若判据在 60 行以下，它要么超读、要么凭感觉动手。把判定压到前 30 行，第二个问题消失。

**为什么「失败长相」放最后而不是最前**：症状是从用户原话进门用的（`index.md` 的症状表已经在做这件事），篇内再置顶会与路由重复；放在末尾，是给动手过程中「这里好像不对」的一次对照。

**判定条目的写法**（§2 的唯一硬要求）：

- 条件在前、动作在后：`若 … 则 …`、`有 … 用 …`、`改了 X 之后要把 Y 复位`。
- 判据必须是任务里能看见的东西（有没有 URL、是不是互斥值、有没有后台刷新），不能是「是否合理」「是否清楚」。
- 每条只讲一个判断；两条判断不要用分号粘成一条。

**「二、做完的标准」的边界（可检验，收口时抽查）**：

每一条勾选项必须带本篇特有的对象、数字或控件名。凡是能原样搬进 `stage/06` 而不损失任何信息的，就不许留在 detail —— 那条属于总清单，改写成一句「按 `stage/06` 的清单收口」。

- 合格：`列表入口的位置恢复经一次真实返回验证：第 3 页进详情再返回，不回第 1 页`（本篇特有、可判定）。
- 不合格：`每个字段要有持续可见的 label`（跨篇通用，该归 `stage/06`）。
- 收口抽查：17 篇改完后，随机取 5 条 detail 勾选项，去 `stage/06` 里找有没有等价条目；有 → 说明这条边界没被执行，报上去。

## 3. 长度上限

**上限 110 行 / 篇；目标 60–100 行。** 现况 49–213 行（中位数 94，最长 `03` 213，最短 `16` 49），同一层内差 4 倍，等于让「篇」这个单位的成本不可预测。

依据三条：

1. **预算算得清**：`SKILL.md` 允许一次取 3 篇。3 × 110 = 330 行，加 `SKILL.md` 102 行仍在 agent 一次能消化完的量级内；若上限取 213，三篇就是 640 行，等于把「按需取两三篇」变成「取三篇就读不完」。
2. **和 `index.md` 的成本模型对齐**：那张表把行数写成「加载成本」，它要给的是一个能用来决策的数。
3. **110 行足够装下门槛 + 代码 + 边界**：`01`（105 行，含 mermaid 图与两张表）、`06`（105 行）证明这个量级能自足；`03` 的 213 行里约一半是同一批对齐规则的展开复述，压缩后不丢东西。

**超限（> 110 行）的唯一合法情形**：压到 110 行以下会违反 §4 的必须保留清单。此时允许超限，但必须同时满足三条：

1. 在第 3–5 行块之后、`## 一、先判` 之前，单独一行：`> **超限理由**：<具体是哪条判据/证据留不住>`。
2. 在回信里单独列出这篇与它的超限理由。
3. 不得为了让数字好看而删结论——§4 就是为这一条存在的。

**除此之外超上限怎么办**：优先删 §5 命中的形态；仍超，停下并在回信里说明「压缩到这里会丢哪条证据」，由主会话裁决。**不许**新建文件、不许把一篇拆成两篇、不许把内容挪到别的篇。

## 4. 必须保留（逐条给出检验方式）

| # | 保留项 | 检验方式 |
|---|---|---|
| R1 | 数值三分标注：每个数值要么注明它是标准要求 / 平台约定 / 项目起点，要么明确是「示例值」 | 篇内出现 `px`/`ms`/`:1`/`×`/`pt`/`dp`/`rem` 的判定句，逐句检查是否可归类 |
| R2 | WCAG 与 APG 的具体门槛与条号（`4.5:1`、`7:1`、`3:1`、`24×24`、`44×44`、`2.4.7`、`2.4.11`、`2.4.13`、`2.5.5`、`2.5.8`、`1.4.10`、`1.4.13` 等） | 改前的数字与条号集合 ⊆ 改后集合（脚本逐项比对） |
| R3 | 代码片段（fenced code block）：CSS / HTML / text 图 / mermaid | 围栏数 ≥ 改前；块内文字不得改写（缩进可调，语义不动） |
| R4 | 「为什么」：一条判断背后的原因，一句话即可 | 每条判定若有原因为什么，保留一句；不得只留规则 |
| R5 | 失败症状的用户原话（`下拉一点就关`、`日期差一天` 这类） | 全文检索，原有原话不得丢失 |
| R6 | 边界与例外（「不是所有边框都要 3:1」「装饰分隔线不承担识别」） | 改前的否定式边界条数不得减少 |
| R7 | 参考链接：篇末 `参考：` 一行内的全部 URL | URL 集合与改前逐条一致 |
| R8 | 第 3–5 行那三行块：`适用`、`本轮不可交付时` 两行一字不动；`读完能判定` 可压到一行但判断对象不得减少 | 与 0.8.1 版逐字对比 |

## 5. 必须删除（逐条给识别特征，不给类别名）

每条都写成「怎么认出来」+「删到什么程度」+「什么不是它」。

### D1 · 顺序阅读框架

- **识别特征**：行首是 `[系列目录](…) · 上一篇：… · 下一篇：…`；或句子含 `本系列`、`这个系列`、`上一篇`、`下一篇`、`见第 N 篇`、`系列会按实际…扩充`、`不能以篇数判断`。
- **删到什么程度**：整行 / 整句删除。篇末 `参考：` 行不属此类（保留）。
- **不是它**：`改读 09`、`详见第 12 篇` 这类**执行期依赖**（真的要到那一步去读）保留，但只允许出现在第 4 行块与第五节，不许在正文里做章节级预告。
- **副作用**：会减少全库相对链接数。正文里的 `见第 15 篇`、`下一篇：[X]`、`[系列目录](…)` 全部计入删除项（它们的去处已经由第 4 行块与第五节承担）；报告里要写「本篇相对链接 8 → 3，减少的 5 条全是 §D1 的导航/预告链接」，主会话据此核对总数，而不是把它当断链。

### D2 · 劝说性开场

- **识别特征**：`#` 标题后第一段（或第一个 H2 前的那段）满足两条以上——出现第二人称「你」；含「可能…却…」「看着就是乱」「显得松散」这类评价；**不含**任何门槛、数值、条号、条件。
- **删到什么程度**：整段删除。它承载的问题意识若在别处没有，压成一条判定放进第一节（一句，不带情绪词）。
- **不是它**：以「项目详情里，名称、负责人和截止日期的字号都一样，却依然有层次」这类**带具体对象**的定位段——如果它后面紧接着判据，压缩成一句留在第一节即可，不必全删。

### D3 · 场景复述式铺陈

- **识别特征**：连续两句以上描述同一个虚构用户的操作序列（`用户输入 A，自动保存开始；随后继续改成 B…`），且该段内没有判据、没有门槛。
- **删到什么程度**：压成一行 `案例：…`，或直接删；判据已经写在第一节的，整段删。

### D4 · 旁支工具教程

- **识别特征**：小节标题含 `录一次`、`用工具`、`打开浏览器开发工具`、`Performance`、`怎么取证`，正文是操作步骤（点哪个面板、录多久、看哪条轨迹）。
- **删到什么程度**：**删动作、留判定**。步骤全删；步骤里夹着的判定（如「看到函数名不等于每次发生强制布局」「不把两次 rAF 间隔冒充 INP」）并入第二或第五节，保留原句。
- **不是它**：`验收路径` 这类「拿真实数据走一遍」的清单——那不是工具教程，是验收动作，压进第二节的打勾项。

### D5 · 对具体素材的免责

- **识别特征**：`本篇由…引出`、`未取得…源码`、`不能据此确认那个页面`、`以下解释这种技术路线及其边界`。
- **删到什么程度**：整句删。**技术边界本身保留**（`自绘光标只覆盖桌面精细指针下的单行 ASCII，其余回原生` 不在删除范围）。

### D6 · 重复自证

- **识别特征**：同一条边界在同一篇里以两种说法各出现一次，或一个已经由本节表格给出的结论，紧接着又用散文复述一遍。
- **删到什么程度**：留一处（表格优先于散文，判定优先于例子）。
- **不许**跨篇合并、不许以「别篇已经讲过」为由删掉本篇的唯一依据。

### D7 · 元描述（介绍这套材料自己）

- **识别特征**：`这套文件是…的执行摘要`、`文章回答"为什么"，这里只回答"做什么"`、`这个文件只是入口与路由`。
- **删到什么程度**：整句删。这类话属于 `README.md` 与 `references/stage/README.md`，不属于单篇。

### 不许删的「看起来像上述某类」

- 带具体对象与条件的开场（`项目详情有"概览、成员、设置"` + 紧接着的判据）。
- 篇末 `参考：` 的 URL。
- 表格里的示例文案（`还没有项目` `创建项目`）——那是判据的载体。
- 章节之间的承接句若承载判据（`导航抽屉分 temporary/persistent/permanent` 这种分类本身是判据）。

## 6. 判定「调整到位」（第三方机械可查）

八条全过才算到位。命令在 `D:\project\skills-repo\skills\ui-detail` 下跑，`$f` 是被检文件。

1. **行数**：`(Get-Content $f).Count` ≤ 110；若 > 110，文件里必须有 `> **超限理由**：` 一行（§3），否则判不通过。
2. **必备小节齐全且顺序正确**：`Select-String -Path $f -Pattern '^## '` 的输出里，`一、先判`、`二、做完的标准`、`五、失败长相与边界` 三条都在，且 `一` 在 `二` 之前、`二` 在 `五` 之前；若出现 `三`、`四`，位置必须在 `二` 与 `五` 之间。
3. **删除特征零命中**：`Select-String -Path $f -Pattern '本系列|这个系列|上一篇|下一篇|系列目录|你可能|这篇由|未取得'` 无输出（`改读`/`详见第` 不计）。
4. **代码不丢**：围栏数 `(Select-String -Path $f -Pattern '^```').Count` ≥ 改前值；改前为 0 时本项豁免。
5. **数字与条号不丢**：抽取改前所有 `\d+(\.\d+)?(:1|\s*(px|ms|pt|dp|rem|%|×))` 与 `\d\.\d\.\d+`，逐项确认改后仍存在。
6. **链接与锚点不坏**：`python scripts/check-links.py .` 对该文件零 BAD（`references/index.md` 行数表变红属预期，见 §8）。
7. **参考链接不丢**：篇末 `参考：` 行内 URL 集合与改前一致。
8. **没有新增立场**：改后不得出现改前没有的 WCAG 条号、门槛值、组件名结论；差异只能是「压缩、调序、删形态」。

## 7. 明确不做

- 不新增设计观点、不新增判据、不新增门槛数字，不改变原文立场。
- 不删除证据（标准原文、条号、门槛、代码、失败原话、边界例外）。
- 不合并两篇，不拆分一篇，不新建文件，不改文件名、不改篇序。
- 不改标题：`# NN · …` 的编号与标题文字一字不动。
- 不动第 3–5 行块的第一行（`本轮不可交付时`），也不动它的措辞。
- 不改 `README.md`、`references/index.md`、`references/stage/**`、`SKILL.md`、`scripts/check-links.py`（见 §9）。
- 不做排版美化（不调整空行风格、不统一标点）、不翻译、不改术语译名。

## 8. 与 `skills-repo/AGENTS.md` 的关系

- 本标准的删除项 D1–D7 全部落在**正文形态**上，不触碰 `AGENTS.md` 第 20 条管辖的 `description`；第 4 行块本身就是那一轮按第 20 条写成的「可执行中止条件」，本标准要求原样保留。
- **冲突点（已知，需主会话裁决，不由子 agent 处理）**：`AGENTS.md` 第 20 条后半与 §6「同一规则只维护一处」的精神，与 §2 要求每篇自带 `二、做完的标准` 存在张力——`references/stage/` 已经是一份执行层清单。本标准的处理：detail 的「先判/做完的标准」只写**本篇特有**的判断，stage 写**执行顺序与跨篇收口**；两者若出现逐字重复，删 detail 侧那句、保留 stage 侧的条目，并在 detail 里改成一句 `按 stage/NN 的清单收口`。此处理需主会话确认后生效。
- **`index.md` 行数表会红**：`scripts/check-links.py` 现在把 `index.md` 的行数表与实际行数机械比对。任何一篇调整后，该表必然报 `line count 94 != N`。**这是信号，不是噪音**：表由主会话在全部篇调整完后统一重生成（`index.md:11` 的「本文件 145 行」「阶段篇 64–86」「详解篇 49–213」三处数字同步改），子 agent 不许碰这张表。
