# 方案写评闭环

主会话写方案、核实评审意见、在授权内选解法；独立评审 Agent 查依据、提问题、复核修改。评审不代替用户授权。

**三个角色**：**执行 Agent**＝照方案动手的一方，只读方案正文，不读记录；**用户**＝授权与验收的一方；**主会话**＝写方案、管记录、派发与判定的那一方。判据里不写"人""读者""实施者"，必须写成这三者之一。

**两份产物，各有唯一消费者**：

| | 开工方案 | 评审记录 |
|---|---|---|
| 读者 | 执行 Agent | 主会话与用户 |
| 只回答 | 从哪开始、按什么顺序、每步怎么判成功、哪里不能动、缺什么必须停 | 当初为什么这么定、评过什么、还剩什么没关、结论是什么 |
| 判别句 | 删掉这句，执行 Agent 会不会做错动作？不会就搬去记录 | 删掉这条，还答得出"当初为什么这么定"吗？答不出就补 |

**用词**：**一路**＝一个独立评审分工，由一名 Agent 承担。**评审者**＝某一路 Agent 的通称，不指主会话。**一轮**＝全部评审路对同一冻结版本完成的一组评审。**一档**＝替代解法的甲／乙／丙三种改动尺度。**收口**＝本轮不再修订、转入交付或实测，不等于通过。**可披露项**＝判定过、两问句都不成立、但仍未关闭的问题。

**强度词只有五个，各有唯一写法**：**必须**＝硬闸，做不到即不合格；**不得**＝禁止；**应当**＝默认做法，可偏离，但必须在记录里写明理由；**可以**＝可选；**只可**＝唯一许可。同义写法不出现：须→必须、一律→必须、不许／不要／禁止→不得或改成肯定式、应→应当、只能→只可。改动强度词按实质修改处理。

**一个概念只用一个词**：严重度变化写"下调严重度"，不写"降级"；"降级"只指把核心前提降级为已披露的残余风险。

**硬闸与建议分开放**：硬闸句用**必须／不得**，默认做法用**应当**。原因、沿革、为什么这么定，只写进记录（字段见[评审协议](references/review-protocol.md)「最小记录」）与设计理由文档，不混在硬闸句里。

## 启动与强度

- 已有方案时先读原稿与评审记录，核对目标、范围、约束、已确认决策。信息够了直接开工；缺的信息会影响方案选择时才问用户。
- 用户指定的评审人数、严重度、轮次、结束条件优先。用户指定正式领域流程的，按该流程分工与检查，不另加一套审批。
- **强度按"照它做、做错了会怎样"选，不按方案多大选。选择依据写进记录。**

| 档 | 判据 | 路数 |
|---|---|---|
| **轻评** | 四条同时成立：①改动可逆，出错能直接撤回；②不触碰用户可见的数据、对外行为与已发布契约；③无迁移、无切换、无新增依赖；④没有"一旦选错、后续步骤全要改"的选择点 | 单路：「对抗」 |
| **常评** | 可逆、限单文件或单模块、不改用户可见行为、无迁移与切换，但**存在至少一个关键选择点** | 两路：「目标与实现」＋「对抗」 |
| **重评** | 涉及共享接口、数据迁移、切换与回退、不可逆操作或多人协作 | 三路：「目标与实现」「运行与演进」「对抗」 |

- 轻评四条必须**逐条写明成立依据**；写不全或任一条不成立即按常评，代价判不出来的也按常评。用户指定单路的同样要写明。
- **三档只决定派几路。** 决策登记表、未核实台账、盲区表不分档，必须写进记录。它们在记录里，不占方案篇幅，所以轻评不再需要"免表"这种豁免。
- 改档必须写明哪几条判据变了，并指定被撤那一路的职责由哪一路承接；升档、降档都留痕。**不得"没满足轻评四条就少派一路"。**
- 各路必须用中文名，不写成 A／B／C——字母会和替代三档的甲／乙／丙混读。
- 轻评从一开始就单路，允许同一路兼任扫描与闭环表核对，记录里注明"本路兼任，独立性已放弃"。

**预算：全程至多 10 轮**，三档相同，不按档位浮动；用户明确指定更早的数字时以其为准。换人、补路、切换解法、恢复执行都不重置已用轮数。

### 什么时候读哪个文件

| 文件 | 什么时候必须读 | 读到什么程度 | 不读会错在哪 |
|---|---|---|---|
| [多路评审](references/multi-route-review.md) | 启动分工、汇总各路意见时 | 完整读完 | 分工重叠、汇总按票数 |
| [评审协议](references/review-protocol.md) | 冻结与落盘、派发、写记录字段、出现争议、判停止、审计、故障恢复、核实实跑前提时 | 按节读：读到哪节就完整读完哪节，不得取单句 | 快照错位、复评凭记忆、记录字段缺项、把记录塞给执行 Agent |
| [对抗路](references/adversarial-review.md) | 派发对抗路之前（主会话与该路 Agent 都读） | 完整读完 | 只给风险清单，构造不出反例 |
| [替代路](references/alternative-review.md) | 启用任一档替代时、算替代路占不占轮次时 | 完整读完 | 候选与当前方案不可比、轮次算错 |
| [评审要点清单](references/review-checklists.md) | 写守卫、清理表、验收断言，或核对修订表时；扫描路每轮读 A 段 | 只读命中的那一段，读完 | 断言只钉退出码、表体行数对不上 |
| [设计理由](references/loop-design.md) | 要改本 skill 的规则、或想删某条规则时 | 完整读完 | 删掉别的失败换来的防线 |

日常评审不读清单全文与设计理由。读到哪一节，就把那一节完整读完，不取单句执行。

## 核心任务与核心前提

**核心任务**＝用户最终必须实现的结果。**核心前提**＝结果能成立的必要条件；缺了它，依赖它的步骤即使正确也实现不了结果。

两者按消费者分开放。**方案侧**只写三样：核心任务、结果验收口径（出现什么现象算它没实现）、前提不成立时"停下来问"的那条动作。**记录侧**写每个前提的依据、状态与性质判定。

前提状态只有三种：**已证实／待核实／明确不满足**。标"已证实"的核心前提必须给锚点 `文件 :: 符号名` 加一句可证伪条件（"若在该符号内找不到 X，则本条不成立"）；其余断言只注明依据类别，不逐条给锚点。核心前提只收必要条件，不收全部步骤与一般质量偏好。

区分"目标本身的必要条件"与"当前解法依赖的条件"：替代解法可以消掉后者，不能降低前者。

核心前提被证伪时只有两条出路，不得含糊放行：

- **消除依赖**：改用不依赖它的解法；
- **降级为已披露的残余风险**：仅当该前提对本目标不可满足时成立（由上游语义或用户已确认的范围决定）。此时必须同时给三样：不可解的理由、缓解措施、能核查缓解是否生效的验收项，写进记录的风险清单。不得据此声称前提成立，也不得把它写成"部分满足"。

评审者不得反复要求解决已合规降级的前提；主会话也不得用降级绕开本可消除的依赖。

## 轮次与替代解法

每路由一名 Agent 承担，不同路用不同 Agent；主会话自评不算独立一路。满足通过条件即结束，不必用满 10 轮。

替代解法按**改动尺度**分三档。不得用"要不要加一路"这一个开关判断；每一档的启用条件见下表：

| 档 | 何时启用 | 成本 |
|---|---|---|
| **甲 换路线** | 有依据表明当前解法依赖的核心前提不成立；或当前解法没有可执行的修复动作，但目标可能靠别的机制实现 | 高：首次盲评 |
| **乙 换组件** | 每轮都可启用；尤其同一决策点已被修补两次以上仍不稳时 | 低：直接给候选与推翻条件 |
| **丙 不做／缩小** | 首次派发强制问一次，之后按需 | 极低 |

- 换不换路看改动尺度，不看方案是否通过：出现甲档触发条件立即启用；否则作者每轮自问"本轮争议是否集中在一个决策点"，是则启用乙档，并在记录里写明判断依据。
- 若目标本身的必要条件只有用户决策或外部证据能给出结果，不强迫替代路绕开它，按退出条件交付阻塞状态。
- 哪一档占路、占不占轮次、用户固定路数时怎么办，见[替代路](references/alternative-review.md)「轮次与路数归属」。
- 一轮结束后再补路计入下一轮；某一路失败时其职责由下一轮换新的那一路承接，该轮记为未完成，失败路不记成"无问题"。

## 1. 编写并冻结方案

核对原始需求、当前实现与现有机制，区分已核实事实、待核实假设与拟议行为。**同时产出两份**：方案（给执行 Agent）与记录（给主会话与用户）。写任何一句之前先问它在哪一侧：

> **删掉这句，执行 Agent 会不会做错动作？** 会 → 方案。不会 → 记录。

### 方案侧必备（按此顺序成文）

1. **用户要什么**：一行原话引用，限定范围用。
2. **核心任务与结果验收口径**：什么现象出现就算核心任务没实现。
3. **开工说明**：第一步做什么、后续步骤的先后依赖、每步完成判据、哪一步卡住时是"停下问"还是"按默认继续"。
4. **步骤**：要改或复用的位置（`文件 :: 符号名`）、关键动作、兼容与失败处理。
5. **禁区**：已锁定的约束与用户已确认的决策，引用编号（`决策 3`）。
6. **验收**：可机械执行的断言表。
7. **什么时候必须停下来问**：未成立的前提、超出授权的范围、未决分歧。
8. **盲区清单**：只写「盲区名／什么条件下必须回来」。

方案不写：依据锚点、性质判定、评审历史、分歧过程、问题计数、取舍点清单、每版沿革。**方案首行只写版本号与一句"本方案自足，实施不需要读评审记录"。**

**落盘**：项目内有能指出**路径与行号**的落盘规则就照它（`AGENTS.md`、`README.md`、`docs/CONVENTIONS.md` 等）。指不出这样的规则时，用下面五条：

- 落在 `plans/<主题短名>/`，目录名用小写连字符；文件名前缀在同目录内首次确定后固定不变，默认等于主题短名。
- **本层每版落两份**：`<前缀>-v<版本>.md`（开工方案，读者是执行 Agent）与 `<前缀>-v<版本>-record.md`（评审记录，读者是主会话与用户）；记录每版一份，产出后不再修改。
- `archive/` 存此前每一版正文，**每产出一版新的就立刻把上一版移进去**。
- 版本号写在正文里，记录文件名用产生它的那一版，被评版本写在记录首行标题。**把文件名当版本号会系统性错位一版**。
- 用户要求不落盘或只要对话稿时，本节不适用，按第 5 节「三条简化口径」处理。

不得在方案里另定一套。

### 记录侧必备

记录是**决策的唯一源**：方案里引用决策只写编号，理由全部在这里。分节与最小字段见[评审协议](references/review-protocol.md)「最小记录」，本节只规定它必须能回答什么：

1. **结论**：通过／部分交付／未收敛退出，加一句为什么。
2. **当初为什么这么定**：决策登记表——3–5 个关键选择点，一旦选错、后续步骤全要改的地方。每点编稳定编号（`决策 1`…），四列：

| 编号 | 选定实现 | 依据 | 什么证据会推翻／备选 |
|---|---|---|---|
| 决策 1 | …… | …… | …… |

`依据` 列写两段，用 `；` 分隔。第一段是依据本身：锚点，或"命令＋exit code＋结论"。第二段是性质与级别：事实／偏好／待核实三选一，写成完整一句。三段式模板、附录行、取舍点清单这个派生视图，见[评审协议](references/review-protocol.md)「最小记录」。

它连同「替代解法的选择理由（哪些候选被拒、凭什么）」一起，是"当初为什么这么定"的唯一住所；方案侧不出现这两样。

**性质怎么判**：能用一条命令、一次检索或读一个符号跑出答案的，就是事实，**当场跑掉，不留待办**；跑不出来且后续步骤的输入依赖它，就是阻塞级偏好，停下来问用户（给两个具体选项加默认）；其余按默认做，交付时在取舍点清单里交代。分不清先按"能跑就跑"处理，仍分不清按阻塞级。只有要触发不可逆操作、要用户授权、要外部账号或跨天等待的，才算"核实起来麻烦"。这类项入未核实台账并写恢复条件。没核出来的事实不得写成常量。**决策值得问用户却判断没问的，理由写进表，别写进方案。**

3. **还剩什么没关**：可披露项与「停止时仍未关闭的项」，每条写不改的理由＋一句可证伪的判定＋恢复条件。

**读记录不必通读**，主会话与用户各读哪几处见[评审协议](references/review-protocol.md)「最小记录」。


### 前提与写法的两条口径

方案状态与实现状态分开记。快照即本轮评审的完整正文（方案＋记录），收到全部结果前不修改，范围写进记录首行。**实质修改**与**契约精度修订**的定义、升版本与复评口径见[评审协议](references/review-protocol.md)「版本与快照」。

**盲区不放大范围**：能用工具命令清掉的情形（某字段可由对应命令改写）不得写成不可清。写成不可清会让执行 Agent 放弃一条本来能走的路。只有确认无工具可清才进盲区，并逐条写"为何不可清"，进记录。需人工修复的，规定可追溯占位值（如 `unknown-<来源>-<日期>`），并在方案里注明"未经核实"；不得伪造一个看起来像真的值。移入盲区不算新增条款，所以"承认这里不知道"永远比"再加一条机制"便宜；前提是**该缺口不会让执行 Agent 做错动作**，会做错动作的按中问题处理。

### 验收断言必须可判

每条验收项写成可机械执行的一行，三列缺一不可：

| 配方（具体操作序列） | 期望退出码 | 期望输出消息集 |
|---|---|---|

正文里唯一必须自己判的一条：**只钉退出码的断言不合格**。两个不同原因常同码，所以必须同时给消息集，或给能区分两者的观测量。其余四条（按消息数核对、被引用用例必须真实存在、差异类断言、覆盖面自检）见[评审要点清单](references/review-checklists.md)「验收断言可判性」。涉及代码插入的落点与豁免见同一文件 A 段 A4。写断言时按段读完。

## 2. 派发独立评审

**评审者读方案全文，加记录里与决策有关的那一半**（决策登记表与取舍点清单、核心前提的依据与状态、未关闭项）。记录的另一半是评审史：修订表、闭环表、沿革、各路限制。这一半**只给复用路，扫描路不给**，否则扫描路一开口就继承了别人的结论。执行 Agent 只读方案，两半都不给。

**每轮最低配置**：一路未见历史版本的评审者做全量新问题扫描（重读全文、报告新问题）；其余复用路只核对闭环表（读正文以核对所引位置，不做全量扫描）。扫描路的完成标准是全文，复用路的完成标准是闭环表覆盖的位置。复用还是换新的依据见[多路评审](references/multi-route-review.md)。

**独立性由派发消息的内容决定，不由换了哪个 Agent 决定。** 消息里只放五样：目标与约束、材料入口、本路职责、冻结正文（方案＋记录）、核心前提及依据。以下内容不放：评审历史、作者对意见的取舍叙述、其他路的当轮结论。"我们讨论后决定"这类句子必须删掉。工具确实无法隔离上下文时，说明已暴露的材料。这条只约束首次派发与每轮的扫描路；复用路必然持有旧意见。

**评审者只做三件事**：报有依据的问题、给每条未关闭项的两问句取值、给检查范围与限制。收口、通过、部分交付必须由主会话判，评审者不产出"能否收口"的结论。

### 每轮必扫的失败模式

每一路都要主动构造输入去试下面三类写法，不等作者列出可疑点。它们的共同点是**看起来通过、实际放行或丢数据**：

| 失败模式 | 一句判据 |
|---|---|
| fail-open 守卫 | 把非法输入代进去：守卫是拒绝还是放行？放行即缺陷 |
| 存在性与 null 塌缩 | "不存在"与"内容为 null"必须分两态记、分别断言 |
| falsy 合并静默丢数据 | 空容器也 falsy；读路径与写路径必须分开判 |

构造用的代码样例、每条具体要什么，见[评审要点清单](references/review-checklists.md) A 段。另两类**文档撰写规范**（表体行数不等于实际条数、不可清的范围被放大）见同一文件 B 段。扫描路每轮必须完整读完 A 段，其余路按需查。

每轮至少扫描路对以上各项给出显式结论；其余路可只针对改动面核对，看到即报。

派发材料有**五项硬要求**，见[评审协议](references/review-protocol.md)「派发材料」：定向追问；不得凭记忆复评；复用者不得声称盲评；先给改动面再给全文；缺陷证据四件套与按严重度分级。

输出需包括结论、高／中／低计数（仅作摘要）、有稳定 ID 的问题及依据、检查范围与限制。评审者只读评方案与记录：不改原文件、不执行拟议实现、不继续派 Agent、不替用户批准上线。

严重度只有三个取值：

- **高**：核心方向不可行、明显违反目标或授权，或可能造成严重破坏。
- **中**：会导致实施错误、关键兼容断裂或无法验收的具体缺口。
- **低**：不阻碍正确实施的清晰度或维护性建议。

只报有依据的问题，不设数量下限。评审者需要跑命令才能核实而没有工具时，列出所需命令及目的。主会话只在已有授权内代跑，把原始结果交回核实。

## 3. 核实意见、修订并复评

逐条核对**高／中问题**的证据；**低问题不必逐条核证**，可直接归入盲区或取舍点清单（它不参与任何判定）。触发闸门的问题修改完整方案，并更新相关步骤与验收标准；两问句都不成立的按第 4 节登记为可披露项，不改正文。合并重复问题时保留来源与各路新增证据；只有一路提出的问题同样必须处理。

每条修订先判它落在哪一侧：改变动作、顺序、判据或禁区的改方案；只改变"为什么这么定"或补依据的改记录。

### 闭环表（进记录）

每个未关闭项一行，记它怎么关的：

| 问题 ID | 来源路 | 状态 | 依据位置 | 下一步 |
|---|---|---|---|---|
| R1F-02 | 对抗 | 已关闭 | 第 3 节「状态三段」第 2 条 | — |
| R2G-01 | 目标与实现 | 未关闭 | — | 交决策 4 重定 |

状态只有**已关闭／部分关闭／未关闭**三值；"部分关闭"必须写清还差什么。关闭项的「依据位置」必须指到正文的具名位置，指不到按未关闭计。复用路的全部工作就是核对这张表所引的位置。

### 修订表（进记录）

每轮把发现压成一张表，一行一条：

| 来源 | 修订 | 是否改变实施动作 |
|---|---|---|
| R1F-02 | 状态入口守卫改成"存在／内容／版本"三段判断；§4 增 `__init__` 项 | 改（机制级） |
| R2F-03 | 清理表补一行"当前内容尚无通过结论"，与相邻同义项合并 | 不改（措辞） |

三列各写什么见[评审要点清单](references/review-checklists.md) D 段：来源的路名与稳定 ID、修订写到落点、"改／不改"两值的边界。**整列都是"不改"即本轮无动作**；判不清按"改"处理。

### 争议怎么办（过程进记录，结论进方案）

| 情形 | 处理 |
|---|---|
| 事实或严重度争议 | 给原始依据、请提出者复核；证据不足或实质分歧保留未决，不自行下调严重度、不删问题 |
| 满足既定约束的方案偏好 | 主会话在授权内选并说明理由；有更优替代不等于当前方案有缺陷 |
| 两路结论相反 | **不取多数、不取较高严重度**。各给一条可判定的最小验证（一条命令／一个输入／读哪个符号），主会话跑一次、原始结果交双方复核；仍相反按未决计，列入交付 |
| 业务目标、扩权或推翻用户决策 | 列选项与影响交用户决定，继续不依赖该决定的工作 |

每次实质修改后向全部路提供新全文与修改说明（扫描路重读全文，复用路核对闭环表所引位置）。

**改动面要报三样，各附清单，不得合并计数**（写进记录）：触及哪几个决策点；本轮**新增了哪些位置**；本轮**删掉或合并了哪几条**。三条各自的写法与"删除 0"的要求见[评审协议](references/review-protocol.md)「最小记录」。

新发现先过一道判别再决定落点——**能否用一条命令实测？失败是单点还是灾难性的？**

| 能否实测 | 失败重数／严重度 | 去向 |
|---|---|---|
| 不能（授权、语义、数据模型） | 多，或有一条灾难性 | 写进正文（方案） |
| 不能 | 单点、不灾难 | 一行进已知盲区（方案列名，理由进记录） |
| 能 | 任意 | 写成**一条判定**：什么输入／状态下直接判失败，加一句兜底动作，不写机制 |
| 能且已知答案 | — | 写成常量或默认值，不讨论 |

这张表是止膨胀的主要手段：绝大多数"看起来该写进方案"的发现，正确答案是一条判定、常量或盲区，不是新条款。

**两条硬线**：

- **不靠新增条款回应新发现**。判据是内容不是计数：删掉这条，会不会有执行 Agent 因此做错决定？不会则不加；两条规则在说同一件事，先合并再改。新发现要求"加 X"时，先答一句"**为什么这里会缺 X**"。缺口成因若是某个可以删掉的东西，先删那个东西。成因消失，X 就不用加。删成因属于修订正文，必须开轮复核，不算本轮已处置。
- **单轮最多新增一个机制**。"机制"指需要新状态、新参数、新依赖或新时序的改动；单纯加动作步骤不算，但同一轮新增动作超过两处，先合并再改。

超线时先删或合并再改，不写"下轮注意"。

**受影响落点的完整性由复评方核。** 作者给出检索命令与全部命中行，并逐行写处置。清单是否完整，由复评方用第三种相邻模式串再核一次。作者自证不算。检索串怎么构造、逐行处置取哪几个值见[评审协议](references/review-protocol.md)「复评与证据沿用」。

未受影响部分可沿用既有证据，但必须确认仍适用并注明原版本与覆盖范围；只转发旧的"通过"不算当前版本复评。出现以下任一情形时，相关路必须扩大检查范围：改动跨多个模块；改动核心前提与技术路线。扩大范围后必须处理新出现的高／中问题。评审者必须核查实际修改，不能只接受"已修复"声明。细则见[评审协议](references/review-protocol.md)「复评与证据沿用」。

每轮记录按评审协议「最小记录」执行。用户打断或上下文恢复后，从记录与 Agent 实际状态接续，不重复派单。

## 4. 判断继续、通过、部分交付或退出

**通过 ＝ 方案可开工（第一条＋第二条）∧ 记录可审计（第三条）。** 两组判据各自对一个消费者负责，不互相折算：方案全对但记录答不出"当初为什么这么定"不算通过；记录齐全但执行 Agent 照做会走错也不算通过。任一组不满足即继续修订。

### 第一条：方案可开工（对执行 Agent）

只用方案正文，一个没参与过评审的执行 Agent 能不能直接答出下面三问？**只给编号、没有回答的按未完成计**；三问有一问答不出的，不必再看后面。

1. **从哪开始、按什么顺序**：第一步做什么，后续步骤的先后依赖是什么。
2. **每步怎么判成功**：出现什么现象就算这步做对了（命令输出、落盘字段、报错文本）。
3. **哪里不能动、缺什么必须停**：哪些约束已锁定；哪条前提不成立、哪件事没被授权、哪种分歧没解决时必须停下来问，不得自行发明规格。

每题给一句能独立读懂的直接回答，并指到正文的具名位置（步骤编号、节标题、决策编号）。"按需处理""视情况而定"这类落点按未回答计。

**第二条：闸门通过。** 不存在一条未关闭项满足下面任一问句：

- **① 照现状写，执行 Agent 会不会做出与方案某条已写明条文相反的动作？** 以下任一情形同样算本问句成立：
  - 造成关键兼容断裂，或无法验收；
  - 必须自行发明规格；
  - **使被改对象（skill／接口／对外契约）的适用范围发生未经用户确认的变更**。
- **② 照现状写，方案自己写明的核心任务会不会在不报错、验收也不红的情况下没被实现？**「不报错、验收也不红」是加重条件，不是谓词的一部分——核心任务明确落空、但以报错形式出现的，同样算成立。
  - **核心任务本身读不出"出现什么现象算它没实现"**，本问句按成立计（核心任务写不清本身就是缺陷）。
  - **只读方案自己写进来的那一行**。若旁注里有用户原话，把它按"要什么"切成子句，逐句问"核心任务覆盖了它吗"。漏一句即成立。旁注里读不出要求的句子不算，例如寒暄、感叹、无后果的抱怨，但必须注明为何不算。**旁注没有用户原话时，只按核心任务有没有给出可观察的失败现象判。**

**判定主体**：本轮新提出项的 ①② 由提出它的那一路在同一份输出里给出；旧问题由复用路给出；主会话自查项由本轮扫描路给出；提出路本轮失败或已换新时由接续路给出，并注明"接续自判，原路失联"；两路相反按第 3 节争议表处置，其结论也算已判定（属业务目标或推翻用户决策的交用户，答复前保持未关闭）。**没写取值、或写出的取值不构成"两问句都不成立"的，不算已被判定。**

### 第三条：记录可审计（对主会话与用户）

- **① 依据齐全**：决策登记表每一行都有 `依据` 两段与性质判定，或有可核锚点。`依据` 两段的口径见第 1 节，三段式模板见[评审协议](references/review-protocol.md)「最小记录」。两样都没有的按未满足计。
- **② 未关闭项可判**：可披露项与"停止时仍未关闭的项"，每条都写两样：**不改的理由**，加**一句可证伪的判定**。判定格式是"若出现 X，则本条改判为必须改"。写不出第二段的按必须改计：只写理由，"没发现"就会冒充"不成立"。
- **③ 两份对得上**：方案里每个 `决策 N` 编号都能在登记表里找到对应行。方案里由它得出的结论句，与该行"选定实现"一致。编号对不上、或登记表查无此行、或两边说法不同的，方案不合格，本轮不得通过。

**不再开轮的情形**：

- **用满 10 轮**（用户指定更早数字时按该数字）。**例外**：用满 10 轮时，若第一条已满足、第二条未满足的只有一项、且所需编辑点≤3，允许再开一轮。开轮前逐条列出并记入记录。该轮计入预算，**全程至多使用一次**，用过即标记。
- **本轮没有任何可执行动作**。判据看效果不看动作。四种取值算动作：①某项取值从"判不出"变成确定值，查清一处符号、跑通一条命令、读懂一节文档都算；②某个此前不合格的落点／锚点／验收核对动作变合格（"补了"不算，必须指出此前不合格、现在合格）；③某个缺口成因被删掉；④某个必须改项的处置要求被满足，能指出改前改后两段文本。**措辞替换本身不算动作。** "等用户决策"算无动作，该项是否阻塞级只决定交付形态写"阻塞"还是"未收敛"。

**判停止前先就地补齐。** 只差一条命令、一次检索、读一个符号、一节文档或一句核对结论就能定论的项，必须补齐，不算开轮。补齐之后再判。

不再开轮时，把仍未关闭的项逐条写进**记录**的「停止时仍未关闭的项」，每条写「为何仍未关闭」与「恢复条件」；方案侧只写"哪些范围现在不能开工、哪些验收项还不能判"。

**三种交付形态**：

- **通过**：两条判据（方案可开工、记录可审计）都满足。它只表示**在已检查范围和现有证据下，未发现尚未解决的阻碍实施问题**。它不保证没有遗漏，不证明实现、测试或上线已完成。通过不按多数票或平均分宣布。
- **部分交付**：两条对整份方案没法都满足，但其中有一块能**单独**满足两条，且不依赖未关闭项。把方案拆成「已可开工」与「挂着未关闭项」两块。后一块逐条指出卡在哪一条判据、哪个问题或哪个未核实项。恢复条件写进记录：要谁做什么，做到什么程度能并入。已可开工那块的开工说明必须完整、不含未写明的假设；做不到就整份按未收敛退出。部分交付是交付形态，不是通过，不占轮次。
- **未收敛退出**：拆不出这样一块。标明"阻塞／预算用尽／评审未完成"等原因，恢复条件写进记录。**不得把退出写成通过。**

高／中／低计数只作摘要显示，不作为继续或收口的依据，也不得为把计数刷到 0 而开轮。

**候选本身不阻止通过**，但采纳／拒绝加理由必须写进决策登记表；未留痕的候选视为未处理。例外：某候选表明"照当前方案做会白做"（典型是甲档指出核心前提不成立）时按缺陷处理，可直接阻断。采纳候选时，其实施必需条件纳入核查。

## 5. 交付与后续授权

交付两份。**开工方案**给执行 Agent，应当越来越短。**评审记录**给主会话与用户，每版一份，产出后不再修改。

方案里每一行都要能回答"执行 Agent 照它做什么"；回答不了的必须搬进记录。**这是"越来越短"的唯一判据，不按字数。**

**结论与计数只在记录里存一份**；方案正文任何位置不写高／中／低计数，也不写"评了几轮""几路同意"。

### 派发实施时的上下文隔离

方案交付后真的开跑时，给执行 Agent 的只有**方案正文**，加必要的目标与授权边界。以下内容一项都不得给：记录、评审历史、分歧过程、计数、被否决的候选、每版沿革。派发消息的格式、逐项要删什么、执行 Agent 问"当初为什么这么定"时怎么答，见[评审协议](references/review-protocol.md)「派发实施材料」。该节同时给出"消息里不该出现理由"这条判据。

### 通过后

"先出方案"任务到此结束。`交付终点` 必须旁注用户原任务的原话片段；指不回原话的按 `只出方案` 处理，等用户一句话放行再进入实施。声明了 `含实施` 且原任务确实已授权的，通过后沿原授权继续，不增加确认环节。部分交付里「已可开工」的部分可在原授权内先开工，同时推进挂着部分；未收敛不自动转实施。提交、对外写入与发布仍遵守既有授权边界。

通过后进入实施，若发现需要偏离已评正文：改动涉及核心前提或技术路线，保存新版本并重开一轮；其余偏离（步骤实现细节、局部顺序、等价替换）就地改。改完在记录里补一条"实施期偏离"，写明改了什么、为什么、影响哪些验收项，交一路复核。不得以"实施中才发现"为由绕过已评正文的约束，也不得为每条实现细节重开整轮。

### 三条简化口径

- 用户要求不落盘或只要对话稿时，两份产物合并进对话稿末尾，用两个小节标题分开；`archive/` 规则不适用，其余判据不变。
- 轻评方案允许把记录压成"三行版"：结论／决策与依据／未关闭项；但**方案侧仍是完整八项**，不因轻评缩短。
- 部分交付准入仍只看「方案可开工」，不因轻评或预算紧张降低。

**没有独立评审能力时**（无子 Agent、工具不可用）：只可走"单路自查加显著标注未独立评审"。此时必须在记录结论首行如实写"未独立评审"，交付形态按部分交付或未收敛退出判。此情形不算通过。不得把自查写成通过，不得谎称独立评审。
