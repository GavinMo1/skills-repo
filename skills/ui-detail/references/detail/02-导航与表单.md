# 02 · 导航与表单：让用户知道自己在哪、改了什么

> **适用**：页面同时有「跳区域、切内容块、切查看方式」三种看起来一样的切换；或要定字段语义、必填、校验时机、保存模型，以及从列表进详情再返回的落点。
> **本轮不可交付时**：若这一轮的改动只在输入框的聚焦过渡与中文输入法手感，停下并说明「不涉字段语义」，改读 [09-输入框的手感](09-输入框的手感.md)；只在按钮 Loading 与选择器点选时序，改读 [10-按钮与选择器](10-按钮与选择器.md)；只处理未保存与切对象的冲突，改读 [15-保存与草稿](15-保存与草稿.md)。
> **读完能判定**：某个切换控件到底是导航、Tabs 还是分段控件，该不该有独立 URL；导航后标题与焦点落在哪；字段该用哪种控件、保存模型是什么；校验从何时起步、错误显示条件是否会漏掉必填；这块「暂时不能改」该用 disabled、readonly 还是直接显示可复制文本。

项目详情有“概览、成员、设置”，成员区能切列表和网格，设置里有通知开关。如果三处都画成一排按钮，用户很难知道自己是在跳转、切视图，还是修改数据。

## 三种看起来相似的切换

| 问题 | 通常使用 | 行为约定 |
|---|---|---|
| 我去哪个区域？ | 导航链接、Sidebar、Navbar | 可以有独立 URL，支持返回、刷新、分享 |
| 当前区域看哪一块内容？ | Tabs | 有对应面板，键盘操作遵循标签页模式 |
| 同一份内容用哪种方式看？ | Segmented control、单选组 | 选择列表/网格等互斥值 |

Tabs 可以同步路由，甚至每个标签对应一个地址；“切换不改变上下文”只是帮助理解，不能推导出“Tabs 不许改 URL”。若控件实际是导航，优先保留链接的语义与浏览器行为。

Breadcrumb 表达信息层级，例如“项目 / 官网改版 / 设置”，不是用户刚才的浏览历史。App bar 常承载页面标题、导航和操作，不必与 Navbar 完全等同。

步骤条 Stepper 表达流程位置。允许回退有助于修正信息，但付款、签署等已完成步骤可能无法直接重开。应解释可改范围，而不是承诺所有步骤都能点回。

## 列表的其他入口

分页适合需要定位、核对和回访的数据；无限滚动适合连续浏览，但要维护返回位置、加载状态和页脚可达性。“加载更多”能让用户控制节奏，也不自动保证位置恢复。

Tree 用于有实际层级的数据；Accordion 是一组展开区域，可单开，也可多开；Disclosure 是单个展开收起。展开时先保持当前位置，不要无理由自动滚动。

Split button 把常用动作与变体合在一起，例如“创建项目”与“从模板创建”。FAB 强调一个主要动作，是否采用应服从平台和任务；桌面端未必需要。汉堡菜单会降低导航的直接可见性，空间充足时可展示常用入口。

## 导航完成后，用户落在哪里

单页应用改了 URL，不等于完成了导航。新主内容就绪后，更新页面标题，并按路由约定把焦点放到页面标题或主区域；静态标题可使用 `tabindex="-1"` 接受程序聚焦，不必进入日常 Tab 顺序。必要时播报新页面已到达，避免焦点移动与直播区域重复朗读相同内容。

首次进入详情通常从内容顶部开始；浏览器返回列表则应恢复原筛选、滚动和合理焦点。不要在所有路由变化时一律滚到顶部，也别在每次后台刷新时把焦点抢到标题。

慢加载时，要明确“正在进入哪个项目”。URL 已变成项目 B、主体却还显示可操作的项目 A，会造成误编辑。可以展示清晰的加载区域，或保留旧内容并明确标为暂不可操作；旧请求不能在新路由下写回旧项目。

深链接对象已删除、权限已失效时，显示具体原因和返回入口，不要悄悄跳到首页。未保存修改与切换对象的处理见[第 15 篇](15-保存与草稿.md)。

## 表单控件表达的是数据语义

| 控件 | 适合表达 | 需要明确的事 |
|---|---|---|
| Checkbox | 独立选择、可多选、同意条款 | 是否必选、是否有全选和半选 |
| Radio | 一组互斥选项 | 初始是否已选，是否允许不选 |
| Switch | 某个状态的开与关 | 即时保存还是整表提交 |
| Select | 从有限选项中选择 | 选项是否容易扫读 |
| Combobox | 输入并选择建议项 | 能否输入列表外的值 |
| Slider | 调整有范围的数值 | 当前值、步长、精确输入方式 |

Switch 通常让人期待即时生效。若整个设置页统一点击保存，需要清楚显示未保存状态；不应悄悄让开关承担另一种保存模型。Combobox 可以限制只能选已有项；Autocomplete 指补全行为，两者并不总能互换。

“选项超过十个就必须可搜索”过于机械。十二个月容易扫读，八个陌生部门反而可能需要搜索。判断依据是选项长度、熟悉程度、排序与使用频率。

日期选择器尽量支持键入并说明格式；出生日期不适合让人翻几十年日历。标签输入要支持键盘删除与清晰命名的删除按钮。上传控件要提前说明格式、大小限制，并提供进度、失败原因和重试；断点续传需按文件规模与网络场景决定。

## 一个字段至少说清三件事

```text
项目名称                         ← Label：这是什么
[官网改版                    ]   ← 输入内容
2–40 个字符                      ← Helper：规则
```

出错后显示“项目名称不能超过 40 个字符”，并用 `aria-describedby` 等方式把说明、错误与字段关联。错误不能只靠边框变红表达；替换 Helper 时，要保留仍然必要的规则。

Placeholder 用于示例，不能替代持续可见的标签。填写后它会消失；它若承载必要说明，也不能因为颜色淡就免除对比度要求。

## 校验不只取决于 blur

第一次输入邮箱时，刚打一个字就报错容易干扰。合理起点是失焦或提交时提示；错误已经出现后，随输入更新能及时告诉用户问题是否修好。

`touched` 与 `dirty` 的精确定义取决于表单库，常见含义是已触碰与相对初始值有变化。错误显示条件可以是“已触碰或已经提交过”；只写 `touched && invalid` 会漏掉从未触碰的必填字段。

提交失败时保留已填数据，把焦点引到错误摘要或第一个错误字段；异步查重需要处理请求乱序，不能让较早的结果覆盖新输入。服务端仍要做最终校验。

## 禁用和只读不是一回事

原生 `disabled` 表单控件通常不进入 Tab 顺序，也不随表单提交。支持 `readonly` 的原生输入控件仍可聚焦、选择内容并提交；`select` 没有原生 `readonly` 属性。

自定义组件使用 `aria-disabled="true"` 只是提供状态语义，不会自动阻止点击或提交。需要自己实现行为。不要把所有“暂时不能编辑”的内容都禁用；有时直接显示可复制文本更合适。

## 用一次异常流程检查表单

不填必填项直接提交，确认能找到错误；修正一个字段，确认错误及时消失；断网保存，确认内容仍在；恢复网络再保存，确认没有重复提交。再刷新页面，验证“已保存”是真的持久化成功。
